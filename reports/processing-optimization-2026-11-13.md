# Оптимизация оценки резюме

13 ноября 2026 года. Проверка на Mac с 8 ГБ, нативная Ollama,
`qwen3.5:2b-q4_K_M`, контекст 8192, максимум ответа 2048.

## Проблема

Десять резюме по девяти профилям требуют минимум 90 сравнений. Исправление
цитат добавляло полные повторные сравнения: у первого обработанного кандидата
восемь из девяти профилей потребовали повтор. Ошибка позднего профиля теряла
все предыдущие оценки этого кандидата. Общая системная инструкция менялась
при повторе, а пользовательский JSON начинался с отличающихся требований,
что мешало повторному использованию уже обработанного префикса запроса.

## Изменения

- API атомарно сохраняет каждую законченную оценку через необязательный
  `checkpoint` в существующем `POST progress`. Она проходит ту же проверку
  цели, балла, весов и обоснования, что итоговая оценка. Первая сохранённая
  оценка при одинаковом контексте не перезаписывается повторной доставкой.
- Оценщик возобновляет только оставшиеся профили. Контекст привязан к job,
  попытке и режиму, файлу и SHA-256 текста, снимку требований, дате, модели,
  версиям правил/промпта, хешу Python-кода оценщика и настройкам контекста.
  Перед повторным использованием проверяются цитаты по исходному тексту.
  При изменении контекста предыдущие промежуточные оценки не используются.
- Состояние принадлежит API и текущему заданию, общего кэша резюме нет.
  Parser не может записывать такие оценки. Удаление, срок действия задания
  и проверка текущей попытки действуют и для checkpoint. Промежуточные оценки
  не завершают кандидата и не публикуют события завершения.
- Итог по-прежнему принимается только со всеми профилями. После сохранения
  полного результата промежуточные копии удаляются; при потере подтверждения
  сохраняется обычный механизм повторной публикации готового результата.
- Системная инструкция постоянна для профилей и повторов. Полный текст
  фрагмента находится в начале пользовательского JSON; отличающиеся
  требования и замечания для повтора расположены после него. JSON компактный.
- Полная JSON-схема передаётся в Ollama `format`, её текст больше не
  дублируется в системной инструкции. Правила стажа, И/ИЛИ, обязательности,
  намерений, образования, стоп-факторов, цитат и неизвестных сведений сохранены.
- При исправлении цитат повторяются только проблемные критерии/стоп-факторы.
  Остальные ответы сохраняются. Исправление использует полный исходный
  фрагмент; ids и цитаты повторно проверяются, затем данные объединяются
  и рассчитываются прежней формулой. Для замечаний повтора заранее
  резервируется контекст. Длинные документы покрываются целиком.

Миграция БД не нужна: дополнительное состояние находится внутри существующего
JSON задания. Старые progress без checkpoint совместимы с новым API.
Образы backend, guest-api, parser и evaluator пересобраны и развёрнуты;
текущее пользовательское задание продолжено без новой загрузки PDF.

## Проверки

- 145 TypeScript-тестов прошли. Проверены сохранение и повтор checkpoint,
  чужие цели, поддельный балл, отсутствие evidence details, смена контекста,
  удалённое/устаревшее задание, запрет для parser, запрет неполного результата
  и удаление промежуточных копий после полного результата.
- 124 Python-теста прошли. Проверены ошибка позднего профиля без повторного
  расчёта готового, потеря ответа checkpoint, восстановление всех оценок без
  модели, смена файла/требований/модели/правил/кода/job/даты, сохранение
  проверенных ответов при исправлении других цитат, полный текст и глобальные
  позиции цитат. Существующие проверки HR-правил также прошли.
- Архитектурная проверка, Compose и `git diff --check` прошли.
- Настоящая 2B-модель: шесть синтетических примеров до/после дали одинаковые
  баллы, статусы и проверенные месяцы. На входе первого примера количество
  токенов сократилось с 2369 до 1871. Для двух прогретых сравнений общего
  резюме с разными профилями суммарное время сократилось с 10,278 до 8,371 с
  (около 19%). Это маленькая проверка, не гарантия ускорения каждого пакета.
- В текущем настоящем задании API уже сохранил промежуточные оценки профилей.
  В журнале Ollama последние запросы занимали 9,89–14,46 с, чтение нового
  входа 1,27–1,91 с. До оптимизации наблюдались запросы 20–40 с и чтение
  входа примерно 9–13 с. Здесь сравниваются разные последовательные запросы,
  это не контролируемый замер одного полного пакета до/после.
- После развёртывания выполнены 24 чтения настоящего API во время оценки:
  все успешны, максимальная задержка 1,413 с. На момент заключительной
  проверки завершены два кандидата из десяти, ошибок заданий нет;
  для следующего резюме уже сохранены три из девяти оценок профилей.

## Ограничение точности модели

В одном из шести синтетических примеров — две последовательные работы по два
года — модель 2B и до, и после изменений процитировала только один период.
Программа корректно засчитала подтверждённые 24 месяца, однако полный ожидаемый
опыт в примере составляет 48 месяцев. Поэтому это проверка отсутствия
наблюдавшейся регрессии, а не заявление, что все шесть эталонов пройдены.
Оптимизация не устраняет ограничений точности 2B и не заменяет проверку HR.

## Проверка сообщения «анализ завис», 17:26–17:38 МСК

Ollama продолжала отвечать HTTP 200, обработчики и API были здоровы. На начало
проверки готово четыре кандидата, ошибок нет, у текущего резюме сохранены две
оценки из девяти. К завершению проверки готово пять кандидатов, у текущего —
шесть оценок из девяти. Новая загрузка и перезапуск evaluator не требовались.

Найдена ошибка отображения: страница `/processing` показывала только загрузки
за последний час и исключала продолжающуюся отправку после её первого часа.
К тому же число готовых кандидатов менялось только после проверки всех
профилей, а сохранённые промежуточные оценки в интерфейс не передавались.

- Активные отправки остаются в списке независимо от возраста. Ограничение
  «последний час» применяется к завершённой истории; список файлов и общие
  счётчики используют один и тот же набор видимых отправок.
- API возвращает только числовой `profile_progress: {completed,total}`.
  Тексты промежуточных оценок и внутреннее состояние checkpoint не раскрываются.
  Получение статуса по-прежнему не переписывает состояние задания.
- В активном анализе показаны число оценённых профилей и время последнего
  изменения. Это завершённые оценки профилей, а не оценка оставшегося времени.
- Frontend и backend обновлены, evaluator продолжал работать.
- Проверены граница часа, сохранение видимости старой активной отправки,
  скрытие завершённой истории и безопасная выдача числового прогресса.
  147 TypeScript-тестов прошли после отдельного последовательного запуска.
  Первоначальный параллельный запуск со сборкой перегрузил Mac и сорвал
  проверки с короткими таймерами; он остановлен и заменён этим прогоном.
- В настоящем Chrome подтверждено: отправка старше часа остаётся видимой,
  счётчик профилей отображается, ошибок JavaScript нет. К этой проверке
  завершены шесть кандидатов, ошибок заданий нет.
