## Обнаруженные проблемы

### 1. P1 — отрицание высшего образования превращается в подтверждённое соответствие

Место: [evidence_scoring.py:202](../apps/resume-analyzer/app/evidence_scoring.py#L202), особенно строки 205–212. Относится к разделу 2 аудита.

Для требования `Высшее образование` наличие слова `высшее` в цитате безусловно устанавливает `status=met`, `credit=1`, перезаписывая даже корректный ответ модели `not_met`.

Воспроизведение через `verify_and_score` с единственным критерием образования:

| Точная цитата из резюме | Ответ модели | Фактический результат |
| --- | --- | --- |
| `Высшее образование отсутствует.` | `not_met` с этой цитатой | `met`, **100/100** |
| `Неоконченное высшее образование, обучение прекращено.` | `not_met` с этой цитатой | `met`, **100/100** |

100/100 здесь — итог для профиля с одним требованием; в профиле с другими требованиями ошибка добавляет полный вес категории образования. Это ошибка программной постобработки, для её возникновения не требуется неверный вывод модели. Объяснение также ошибочно помещает условие в «Подтверждено».

Исправление: учитывать отрицания, незавершённость и факт получения степени до повышения статуса; при неоднозначности оставлять `unknown`. Добавить эти случаи в регрессионные проверки.

### 2. P1 — упоминание навыка автоматически подменяет смысловую оценку

Место: [evidence_scoring.py:171](../apps/resume-analyzer/app/evidence_scoring.py#L171), `_skill_evidence`, строки 124–155. Относится к разделу 2 аудита.

Для `keyword` программа полностью заменяет статус и доказательства модели результатом поиска названия навыка по всему резюме. Упоминание технологии не проверяется на принадлежность навыкам кандидата; отрицание до соседнего навыка распространяется на последующий.

Воспроизведение для единственного требования `Python`:

| Текст резюме | Ответ модели | Фактический результат |
| --- | --- | --- |
| `В команде коллеги писали на Python; мои задачи: продажи.` | `unknown`, без подтверждения | Python в `matched_keywords`, `met`, **100/100** |
| `Не владею Tableau, уверенно работаю с Python.` | не требуется | Python отсутствует в совпадениях, `not_met`, **0/100** |

Первый случай создаёт неподтверждённую компетенцию, второй превращает явно подтверждённый навык в доказанное несоответствие. Дословность цитаты и правильная арифметика эти ошибки не устраняют.

Исправление: использовать поиск названий как дополнительную проверку смыслового сравнения; не повышать `unknown` автоматически. Ограничить область действия отрицания соответствующим утверждением и проверять, о чьём опыте говорится.

### 3. P2 — проверка актуальности задания выполняется после публикации processing

Место: [consumer.py:77](../apps/resume-analyzer/app/consumer.py#L77), строки 77–83; `check_job_status` находится внутри `process_checked_job`, запускаемого позже. Относится к ANR-1 и ANR-6.

Проверен реальный `run_consumer` с подставленными AMQP-соединением, readiness и ответом backend; сетевых обращений и вызовов модели в этом воспроизведении нет:

| Условие | Наблюдаемая последовательность |
| --- | --- |
| Backend возвращает `completed/false`, модель готова | публикация `processing` → запрос статуса → ACK |
| То же завершённое задание, модель недоступна | публикация retry → ACK исходной доставки; запроса статуса нет |
| Backend временно недоступен, модель готова | публикация `processing` → запрос статуса с ошибкой → публикация retry → ACK |

До скачивания и вызова модели проверка уже есть. Однако завершённые/заменённые задания при недоступной модели продолжают циркулировать через retry; при недоступном backend публикуется начало обработки, хотя разрешение на расчёт не получено. Требуемый аудитом порядок выполнен частично.

Исправление: сначала проверить конкретную попытку, при `false` подтвердить доставку; только затем проверять готовность и публиковать `processing`. HTTP-запрос статуса оставить вне потока Pika.

### 4. Развёртывание — прежняя AMQP-конфигурация несовместима с новым значением по умолчанию

Места: [docker-compose.yml:47](../docker-compose.yml#L47), [docker-compose.yml:103](../docker-compose.yml#L103), [config.py:74](../apps/resume-analyzer/app/config.py#L74). Относится к разделам 4–5 аудита.

Во время проверки локальный `.env` содержит `RABBITMQ_ENABLED=true`, `RANK_BRIDGE_ENABLED=false`, но не содержит `ANALYZER_ADAPTER`. Compose явно подставляет `http`. Новая валидация ожидаемо отклоняет эту комбинацию: `HTTP analyzer requires RANK_BRIDGE_ENABLED=true`.

По журналам analyzer, backend и worker завершаются с этой ошибкой и автоматически перезапускаются. Кроме того, продолжает работать старый контейнер `resume-analyzer-consumer`, которого уже нет в актуальном Compose. Значит, запущенное окружение не соответствует проверенному исходному коду.

Для сохранения прежнего native-режима требуется явно задать `ANALYZER_ADAPTER=amqp`, сохранить `RABBITMQ_ENABLED=true` / `RANK_BRIDGE_ENABLED=false` и выполнить совместное обновление сервисов с удалением старого consumer, как описано в [контракте](../docs/resume-analyzer-rabbitmq-api.md#режимы-приложения-и-подключение-analyzer). Настройки и работающие сервисы в рамках этой проверки не менялись.
