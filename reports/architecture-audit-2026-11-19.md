# Архитектура и организация файлов: проверка 19 ноября 2026 года

## Вывод

Основная схема приложения соответствует целевой архитектуре. Полного соответствия пока нет: остаются дефект очистки незавершённых гостевых загрузок, неполная политика запрета кеширования ошибок API и незавершённый вывод прежней реализации из исходников, тестовых команд и документации.

Перестраивать весь проект или вводить другую архитектурную методологию оснований нет. Организация `apps / packages / infra / db / tests / docs` подходит системе. Нужны адресные исправления и завершение перехода между протоколами.

Основание: рабочее дерево на HEAD `1101106`, включая существовавшие до проверки незакоммиченные изменения интерфейса, контрактов и тестов. Код приложения не изменялся. Основной нормативный документ — `docs/target-architecture.md`; также учитывались `guest-task-lifecycle.md`, актуальные дополнения `processing-services-contract.md`, `scoring-policy.md` и `preparation.md`. Исторический аудит от 11 ноября использован для сравнения, а не как описание текущего кода.

## Что соответствует цели

| Требование | Что найдено |
| --- | --- |
| Один публичный прикладной вход | Frontend/Nginx; в штатной конфигурации API, брокер, БД, S3 и обработчики не публикуют host-порты. Необязательный административный профиль рассматривается отдельно. |
| Разделение гостевого и авторизованного API | `/api/guest/*` и `/api/app/*`, whitelist методов/путей, `auth_request`, закрытые публичному входу internal-маршруты. |
| Auth-check без бизнес-зависимостей | Зависит от `@hr/security` и Express, получает открытый ключ; не имеет БД, S3 и AMQP-зависимостей. |
| Гость без доступа к бизнес-БД | Нет импорта `@hr/data-access`, PostgreSQL credentials и общей сети с backend/PostgreSQL. Временный bucket и отдельные S3 credentials. |
| Общая обработка двух режимов | Один parser и один evaluator, два vhost, отдельные соединения и права по операциям. |
| Самостоятельные Python-сервисы | Разные исходники, точки входа, requirements и Dockerfile; общий транспорт вынесен в пакет. Прежнее приложение `apps/resume-analyzer` отсутствует. |
| Разделение parser/evaluator | Parser не вызывает модель, не входит в сеть модели и не получает LibreOffice; evaluator получает одно резюме и критерии. |
| Доступ обработчиков по заданию | Job-токены, проверка режима/операции/идентификаторов/attempt/deadline; нет универсальных S3/БД credentials. |
| Оркестрация внутри API | `ProcessingEngine` обрабатывает события и создаёт последующие команды. `apps/worker` не включён в основной Compose. |
| Надёжность транспорта | Publisher confirms и mandatory, стабильные ID, сохранение результата до события, ACK после принятия результата, брокерные повторы и DLQ. |
| Различие хранения задач | `AuthorizedTaskStore` и PostgreSQL outbox для сотрудника; S3/CAS без outbox и восстановления заданий сканированием для гостя. |
| Readiness модели | `/ready` evaluator и `probeEvaluator()` в API; наличие consumer больше не является единственной проверкой доступности. |
| Границы frontend | Среди внутренних зависимостей только `@hr/contracts`; нет серверных пакетов и Node.js-импортов. |
| Гостевые данные вне backup | Скрипт S3 backup требует постоянный bucket и отвергает `guest-temporary`. Полное восстановление не проверялось. |

Основание: `docker-compose.yml`, `infra/rabbitmq/init.mjs`, манифесты пакетов, `apps/*/src`, `packages/processing/src`, Dockerfile обработчиков, `scripts/s3_snapshot.mjs`. Конфигурационные границы подтверждены `test:architecture` и `test:compose`; это не полная проверка фактических прав работающего брокера и S3.

## Замечания

### N-01. Средний приоритет: незавершённая загрузка удерживается после таймаута

Требование: `docs/guest-task-lifecycle.md:63` — незавершённая загрузка по таймауту очищается вместе с записанными частями.

В `packages/processing/src/state.ts:35` функция `expireWork()` завершает такую задачу через `finish()`. В `state.ts:33` к времени завершения добавляется обычный срок хранения результата, по умолчанию два часа. `apps/guest-api/src/service.ts:78` пропускает удаление объектов до появления `deleted_at`, которое устанавливается по новому `expires_at`.

Воспроизведено на синтетической задаче возрастом 11 минут с одним частично сохранённым файлом, через настоящий `GuestService.cleanup()` и хранилища в памяти:

```json
{"status":"failed","deleted":false,"retention_after_upload_deadline_minutes":120,"files_remaining":1,"objects_removed":0}
```

Нужно отделить срок хранения готового отчёта от очистки сорванной загрузки: после upload timeout закрывать доступ к содержимому и удалять части, оставляя необходимые технические отметки. Проверять именно удаление объекта, а не только переход в `failed`.

### N-02. Средний приоритет: старый контур остаётся частью обычной разработки

Это долг организации исходников, а не обнаруженный запуск лишнего worker в Compose.

- `package.json:12` включает `@hr/worker` в обычную сборку; строка 15 сохраняет команду запуска `worker`.
- `apps/worker/src/index.ts` запускает прежние storage consumer и rank bridge.
- `packages/data-access/src/index.ts` экспортирует старые `analysis`, `queue`, `import-outbox`, `spool`, `processing-mode` рядом с действующими репозиториями. Эти модули доступны текущему backend через общий вход пакета.
- `apps/backend/src/import-results.ts` одновременно содержит нужный новому контуру `persistResult()` и прежние result/progress consumers; старые функции из `data-access` импортируются в этот же модуль.
- `apps/backend/src/config.ts:11` сохраняет `RESUME_ANALYZER_CALLBACK_TOKEN` и `WORKER_HEALTH_URL`, хотя текущая схема использует job-токены и общий evaluator.

В результате актуальный и исторический пути недостаточно различимы при изменении кода. Наличие старых файлов само по себе не нарушает runtime-изоляцию, но переход на целевую архитектуру на уровне репозитория не завершён.

Нужно отделить общую бизнес-персистенцию от старого транспорта, убрать worker из стандартного пути сборки и явно изолировать оставшуюся совместимость. Сначала проверить обращения и необходимость чтения исторических данных; удалять всё по имени файла нельзя.

### N-03. Средний приоритет: часть публичных тестовых команд проверяет старый API

`npm run test:workflow` запускает `tests/workflow.integration.ts`, где строка 15 обращается к `base + "/api" + path`: например, `/api/overview`, без сессии сотрудника. `npm run test:service-outage` обращается к `/api/analysis/status`, `/api/candidates` и другим прежним маршрутам, ожидая успешную обработку. Текущий Nginx обязан возвращать для них 404. Эти команды не могут подтвердить описанные сценарии через штатный текущий вход без доработки.

Также `test:queue` и `test:rank-modes` запускают проверки прежних очередей и `/rank`; в названиях команд это не обозначено. `npm test` запускает только TypeScript `*.test.ts`, а `npm run build` не собирает Python-обработчики. Интеграция настоящих parser/evaluator вынесена в `tests/run_processors.py`, отдельной npm-команды для неё нет.

Нужно обновить workflow/outage-проверки на `/api/app`, авторизацию и Origin, а прежние проверки обозначить как legacy. Для текущей системы нужен явно описанный набор команд, включающий Python и оба обработчика. Успешный `npm test` не равен полной проверке системы.

### N-04. Средний приоритет: runtime-логи всё ещё отслеживаются Git

`git ls-files` показывает девять файлов в `logs/resume-analyzer*`, включая ротации и диагностические логи. Их общий размер в рабочем дереве — около 10,1 MiB. Добавление `logs/` в `.gitignore` не прекращает отслеживание уже закоммиченных файлов.

Это незакрытая часть критерия прежнего A-07: runtime-логи должны быть исключены из Git и поставки. `.dockerignore` уже исключает логи из build context, но в репозитории они остаются.

В корне также отслеживаются `.DS_Store`, `resume-analyzer-source.tar.gz` и `data.json`. Для архива прежнего сервиса и JSON не установлено назначение в текущей поставке; стоит явно классифицировать их как фикстуры/исторические материалы либо убрать из активной структуры. Наличие чувствительных данных в них в рамках проверки не устанавливалось.

Нужно снять runtime-логи с отслеживания с сохранением нужных локальных копий. Переписывание истории Git не входит в предлагаемый обычный рефакторинг.

### N-05. Низкий приоритет: не все API-ошибки запрещают кеширование

`apps/frontend/nginx.conf:107` и строка 108 возвращают JSON 404 без `Cache-Control`; обработчик `@too_large` в строке 45 также не задаёт его. Это расходится с требованием не кешировать ответы API.

На текущем входе `http://localhost:3000` подтверждено:

| GET | Статус | Cache-Control |
| --- | --- | --- |
| `/api/session` | 200 | `no-store` |
| `/api/app/overview` без cookie | 401 | `no-store` |
| `/api/unknown` | 404 | отсутствует |
| `/api/internal/test` | 404 | отсутствует |

Нужно применить `no-store always` и к fallback-ответам/413. HTTP-проверка 413 не выполнялась; вывод о нём основан на конфигурации.

### N-06. Низкий приоритет: сборочные рецепты и архитектурные проверки расходятся

Основной Compose собирает backend через `infra/node/Dockerfile` с `SERVICE=backend`. Одновременно существует почти идентичный `apps/backend/Dockerfile`. `tests/architecture.mjs:34` проверяет наличие пути приложения в последнем, хотя штатная сборка использует другой файл.

Проверка Python в `tests/architecture.mjs:51` анализирует текст Dockerfile и requirements, но не граф импортов Python. Сейчас разделение правильное; автоматическая защита от будущего импорта evaluator из parser или зависимости общего runtime от одного из приложений неполна.

Нужно оставить один источник сборочного рецепта либо явно описать назначение второго. Для Python добавить проверку направлений импортов и отдельный smoke импорта каждого сервиса в его собственном образе. Общий Node Dockerfile сам по себе соответствует цели, если сохраняется выборочный состав runtime.

### N-07. Низкий приоритет: нормативные документы требуют синхронизации

`docs/architecture.md:7` всё ещё говорит о поставке обработчиков из другой ветки. Они уже присутствуют в `apps/resume-parser` и `apps/resume-evaluator`; текущие README и `preparation.md` это отражают. Исторические разделы v1 в `architecture.md` помечены, но первое утверждение находится до исторического раздела.

Есть и более существенное уточнение границы оценки: `processing-services-contract.md:182` говорит, что приложение не рассчитывает второй балл. Однако актуальное дополнение того же контракта, строка 303, и `scoring-policy.md:3` явно разрешают пересчёт представления старых отчётов для отзыва неподтверждённых дополнительных выводов. Код `packages/contracts/src/evidence.ts:203` и `verifiedRatingView()` реализует именно это исключение; оно используется гостевым API и `data-access/repository.ts`.

Поэтому считать такой пересчёт самовольной регрессией прежнего A-06 неправильно: он описан в актуальной политике от 16 ноября. Но общее правило, исключение и источник канонической оценки нужно связать явно. `contracts` сейчас включает не только DTO/схемы, но и общие правила предметной области и представления; название пакета не полностью описывает его ответственность.

Предпочтительно явно выделить в документации сохранённую оценку evaluator и проверенное представление исторической оценки. При дальнейшем росте кода правила представления можно вынести в отдельный браузерный пакет, сохранив единое поведение API, UI и экспортов. Это рекомендация по сопровождению, а не обязательное требование исходной целевой схемы.

## Приоритет работ

1. Исправить очистку незавершённых загрузок и запрет кеширования ошибок API.
2. Привести workflow/outage-тесты к текущему API; обозначить legacy-команды и собрать документированный набор проверок TypeScript/Python/обработчиков.
3. Разделить текущую персистенцию и старый транспорт; вывести worker из обычного пути сборки; снять runtime-логи с отслеживания и определить назначение корневых артефактов.
4. Согласовать Dockerfile, усилить проверку Python-импортов и обновить архитектурную документацию с учётом политики исторических отчётов.

Дальнейшее деление frontend на features, перенос бизнес-правил из роутов и выделение самостоятельного пакета правил отчёта возможны по мере роста. Отсутствие этих изменений не является нарушением принятой целевой архитектуры.
