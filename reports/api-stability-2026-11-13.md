# Доступность API при анализе резюме

13 ноября 2026 года, время журналов — Москва.

## Подтверждённые причины

- В 14:50–14:53 Nginx возвращал HTTP 503 для `/api/app/overview` и журнала событий.
  Есть `upstream timed out` как для backend, так и для проверки сессии `/verify`.
  Проверка сессии имела таймаут 3 секунды.
- Страница запускала overview каждые 3 секунды и события каждые 2,5 секунды,
  даже когда предыдущий запрос ещё выполнялся. Запросы не отменялись при уходе
  со страницы. После задержки в журнале видна массовая выдача накопленных ответов.
- `importDetail()` при каждом чтении вызывал `mutateTask()`: даже неизменившаяся
  завершённая запись целиком записывалась в PostgreSQL с увеличением версии.
  Получение истории делало отдельные чтения и записи для каждой отправки.
- На Mac 8 ГБ общей памяти. В журнале Ollama есть пики расхода 5,2–6,8 ГБ;
  вместе с Docker и остальными приложениями это создаёт серьёзное давление на
  память. В 14:44 журнал модели показывал отсутствие свободного swap.
  Это усиливало задержки API. Последующее выключение Ollama и оценщика было
  действием пользователя, а не доказанным самостоятельным падением сервера.

## Изменения

- Опрос overview, событий, очереди и гостевых статусов идёт последовательно,
  с ограничением времени запроса, отменой при размонтировании и увеличением
  паузы после ошибок до 30 секунд. Скрытые страницы не опрашивают API.
  Ручное обновление и фоновый опрос overview используют один текущий запрос.
- Последние успешные данные сохраняются. Ошибки по-прежнему показываются;
  запись/загрузка файлов автоматически не повторяется.
- Неизменившиеся статусы больше не переписывают `processing_tasks`.
  История читается страницами по 100 записей. Реально истёкшее задание
  по-прежнему обновляется через повторное чтение и compare-and-set;
  восстановление ошибок повторной оценки сохранено.
- Таймаут чтения проверки сессии увеличен до 10 секунд, подключения — до 5.
  Проверка авторизации остаётся обязательной.
- Только для Mac overlay: контекст 8192 вместо 16384, максимум ответа 2048
  вместо 8192, неиспользуемая модель выгружается через 30 секунд.
  Исходный текст не обрезается. Для ограниченной памяти Mac с согласия
  пользователя выбрана более лёгкая модель `qwen3.5:2b-q4_K_M`;
  исходные варианты 4B сохранены. Меньшая модель может оценивать менее точно.
  Вариант можно переопределить через `MAC_OLLAMA_MODEL`.
- Только для Mac overlay: общий бюджет задания увеличен с 30 минут до трёх
  часов (`MAC_PROCESSING_TIMEOUT_MS`). Это предел ожидания для последовательной
  проверки нескольких резюме по нескольким профилям, а не обещание скорости.

## Проверка

- 141 TypeScript-тест: отсутствие перекрывающихся запросов, отложенные
  повторы и восстановление, отмена запросов, скрытая страница, единый запрос
  для ручного и фонового обновления; чтение 125 отправок за 3 SELECT без UPDATE;
  сохранение таймаута задания ровно один раз.
- Добавлен один повтор безопасного GET/HEAD при HTTP 502/503/504 или обрыве
  соединения. Две попытки используют общий deadline. POST/PUT/PATCH/DELETE,
  ошибки авторизации и загрузки файлов автоматически не повторяются.
  Прерывание ожидания отменяет повтор. Постоянная недоступность остаётся видимой.
- 118 Python-тестов прошли с параметрами 8192/2048, включая ограничения
  JSON-схемы конкретными id и их количеством, исправление неполного ответа
  повторным запросом и неизменность общей схемы между профилями.
- Для всех 90 сочетаний десяти резюме и девяти демонстрационных профилей
  проверено полное покрытие текста: максимум два фрагмента, без пропусков.
  Это проверка контекстного бюджета, без обращения к реальной модели.
- Архитектурные проверки, Compose и `git diff --check` прошли.
- После обновления frontend и backend выполнены 9 настоящих чтений API под
  `hr-admin`: overview, статусы импортов и журнал событий. Все HTTP 200,
  максимальная задержка 0,046 секунды. Версии всех 10 завершённых отправок
  сохранились. Дополнительно подтверждена видимость 9 активных демонстрационных
  профилей. Модель при этой проверке выключена.
- Оценщик пересоздан без запуска: в сохранённой конфигурации контейнера
  подтверждены 8192/2048/30s. На этом этапе Ollama не запускалась.
- При повторной проверке сообщение о потере API на свежей странице не
  воспроизводилось. Проверен настоящий Chrome с отдельным временным профилем:
  вход HR и загрузка требований, медленный ответ, один искусственный HTTP 503,
  затем два последовательных HTTP 503 и восстановление настоящего API.
  Краткий сбой переживается повторным чтением; постоянный показывается в
  уведомлении; после восстановления уведомление исчезает автоматически.
  Одновременно выполнялся максимум один overview, ошибок JavaScript нет.
  UI теперь различает неудачную первоначальную загрузку и обновление ранее
  полученных данных; добавлена кнопка перезагрузки страницы.

## Загрузка исходного PDF и повтор с разрешения пользователя

- Обычная multipart-загрузка исходного `resumes-first-10.pdf` (4 731 673 байта)
  возвращает HTTP 202 за 0,34 секунды. Настоящий Chrome также принял этот PDF:
  показал экран принятой отправки, ошибки overview и JavaScript отсутствовали.
  Для проверки parser временно приостанавливался, затем был восстановлен;
  созданы и удалены только собственные проверочные отправки.
- Исходная пользовательская отправка уже содержала десять распознанных резюме.
  Все десять оценок завершились `PROCESSING_TIMEOUT` после истечения общего
  30-минутного срока. Файл при загрузке не терялся.
- После явного разрешения пользователя создана новая отправка из сохранённых
  файлов: десять резюме, девять демонстрационных профилей, неизменяемый снимок
  требований и новые идентификаторы заданий. Повторной загрузки и повторного
  разбиения PDF нет; команды отправлены через обычный durable outbox.
- Реальная оценка старым тегом `qwen3.5:4b` даже с контекстом 8192 воспроизвела
  нехватку памяти: Ollama сообщила пик 5,37 ГиБ, swap вырос до 6,1 ГБ,
  Docker Engine вернул HTTP 500. Оценщик приостановлен, модель выгружена;
  повторное задание и файлы сохранены. Поэтому успешные проверки чтения API
  при выключенной модели сами по себе не подтверждают работу под нагрузкой.
- Явный GGUF-вариант `qwen3.5:4b-q4_K_M` скачан и проверен: первые два
  обращения к модели завершились HTTP 200 за 60 и 42 секунды. Однако чтения
  API затем замедлились до 15–17 секунд и зарегистрирована HTTP-ошибка.
  Одной смены поставки 4B оказалось недостаточно. Оценщик приостановлен,
  модель выгружена; задание сохранено.
- Пользователь явно одобрил переход на более лёгкую 2B с возможным снижением
  точности. Mac overlay и пример конфигурации переключены на явный
  `qwen3.5:2b-q4_K_M`. Модель скачана, оценщик пересоздан и запущен.
  `/api/ps` подтверждает именно этот тег, контекст 8192 и 1 685 585 918 байт
  памяти модели. Первые четыре обращения `/api/chat` завершились HTTP 200
  за 14–22 секунды. Восемь параллельных по времени проверок overview/статуса
  отправки прошли без ошибок, максимум overview — 0,199 секунды.
  Readiness доступен и для гостя, и для HR. Это подтверждает начало работы
  под настоящей нагрузкой; завершение всех десяти резюме пока не заявляется.
- При первом проходе 2B обнаружен `ModelResponseError`: незавершённая оценка
  корректно вернулась в очередь вместо записи неподтверждённого результата.
  Для ошибок формата/списка id прежний повтор использовал одинаковый запрос
  с температурой 0. Теперь схема ограничивает допустимые id и точное число
  элементов для конкретного профиля, а повтор получает корректирующую
  инструкцию. Полнота id и цитаты по-прежнему проверяются программой.
  В технический журнал добавлен этап ошибки без текста резюме или ответа.
  Образ пересобран, оценщик перезапущен; сохранённое задание не дублируется.
- Итог настоящего прохода после обновления оценщика: в 16:43:53 первый
  кандидат завершён, девять оценок сохранены, `receipt.resume_id` присутствует,
  ошибки проекции отсутствуют. Остальные девять резюме продолжают обработку,
  ошибок заданий на момент проверки нет. Все 36 проверок overview и статуса
  отправки за шесть минут под нагрузкой успешны; максимальная задержка overview
  1,201 секунды. Повторно подтверждена доступность обработки для гостя и HR.
  Это проверка завершения первого кандидата, а не утверждение о готовности
  всего пакета или неизменной точности модели меньшего размера.

Изменения формулы оценки и миграция БД для этого исправления не нужны.
