# Исправление готовности модели после долгого анализа

Загрузка: `3105971f-9d02-4b10-a44c-908fa7458480`.
Исходный результат: два успешных резюме, три ошибки `DELIVERY_LIMIT_EXCEEDED`.

## Причина

Фоновый монитор и анализ используют один `model_lock`. Во время анализа монитор
не обновляет отметку проверки Ollama. Проверка считается свежей 35 секунд,
а первый успешный анализ занял около 147 секунд. После освобождения блокировки
следующее задание получало `ModelUnavailable` до следующего запуска монитора.
Повторные отказы расходовали лимит доставок RabbitMQ.

Все пять PDF доступны и прошли проверку SHA-256. В журнале Ollama за исходную
обработку восемь запросов `/api/chat`, все с HTTP 200. Ошибка готовности
воспроизведена отдельно; исходные причины каждой доставки прежде не логировались.

## Изменение

`model_capacity` сначала получает блокировку, затем отдельно проверяет возраст
последней проверки. Если она устарела, выполняет ограниченную по времени проверку
Ollama перед началом следующего задания. Реальная недоступность по-прежнему
останавливает анализ; таймаут проверки освобождает блокировку. Вложенные обращения
к модели сохраняют общую блокировку. Добавлены проверки отмены вокруг запроса
готовности и безопасный журнал класса ошибки модели и технического ID задания.

Обновлён только контейнер `resume-evaluator` с локальным Ollama overlay.

## Проверка

- До исправления тест последовательных долгих заданий воспроизводил отказ.
- После исправления прошёл 31 тест: `test_readiness`, `test_service_runtime`,
  `test_processing_v2`. Настройки кэша соответствуют запуску worker v2.
- Пять новых регрессионных тестов проверяют долгие задания подряд с виртуальным
  временем, реальную недоступность, таймаут с восстановлением, свежий отрицательный
  результат проверки и вложенную блокировку модели.
- `git diff --check` прошёл.

Повторные задания уже находились в очереди во время установки исправления.
После обновления все три задания завершились успешно. Штатный API подтвердил:
`processed_files=5`, `failed_files=0`, `pending_files=0`, у всех пяти элементов
есть сохранённые `resume_id`. Наблюдение после обновления заняло 315 секунд.
Проверка БД подтвердила, что два исходных успешных задания сохранили прежние
`job_id`, первую попытку и успешно применённые результаты.
