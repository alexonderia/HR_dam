# Проверка целевой архитектуры и развёртывание

Дата: 11 ноября 2026 года. Исходный commit: `38ca330`.
Основание: `docs/target-architecture.md`, `docs/guest-task-lifecycle.md`,
`docs/processing-services-contract.md`. Проверены исходники, разрешённая модель
Compose, сборка и автоматические тесты; эксплуатационные проверки описаны ниже.

## Вывод

Основные границы целевой архитектуры реализованы: два API-контура, отдельная
проверка сессии, общий prepare/evaluate, оркестрация событиями RabbitMQ и разные
механизмы хранения гостевых и постоянных данных. Проверки импортов и Compose
проходят. Полное соответствие требованиям организации сервисов, жизненного цикла и наблюдаемости
не подтверждено: найдены расхождения жизненного цикла, статуса готовности,
заголовков ошибок API и эксплуатационной документации. При проверке отчётов
также обнаружена ошибка интерпретации стажа в оценщике (A-05). Попытка
компенсировать её в слое представления нарушала разделение ответственности;
эта компенсация удалена (A-06), исходная ошибка оценщика остаётся открытой.
Замена прежнего анализатора двумя самостоятельными сервисами завершена только
на уровне запуска контейнеров: исходники, зависимости и сборка всё ещё связаны
с `apps/resume-analyzer`, а прежние точки входа сохранены (A-07).

Уточнение пользователя от 11 ноября 2026 года: прежний анализатор должен быть
полностью замещён `resume-parser` и `resume-evaluator` согласно целевой
архитектуре. Сохранение прежнего анализатора как третьего поддерживаемого
сервиса или альтернативного штатного способа обработки не является целевым
результатом миграции.

Аудит не изменяет бизнес-логику. Для запуска изменён только локальный `.env`:
устаревший `COMPOSE_PROFILES=broker` заменён на `processing,docker-ollama`.
Подготовка окружения сохранила существующие ключи и настройки.

## Соответствие требованиям

| Требование | Результат и основание |
| --- | --- |
| Единственный публичный прикладной вход Nginx | Выполнено: frontend публикует только `127.0.0.1:3000`; API, БД, S3, AMQP и модель не публикуют host-порты. Административный профиль не включался. |
| Явные маршруты, `auth_request`, закрытые internal API | Выполнено: `apps/frontend/nginx.conf`; проверены 401/403/404 на публичном входе, `nginx -t` проходит. |
| Auth-check без БД, S3, AMQP и приватных ключей | Выполнено: исходники `apps/auth-check`, зависимости и Compose; сервис получает только `auth-public`. |
| Гостевой API изолирован от бизнес-базы | Выполнено: нет зависимости `@hr/data-access`, PostgreSQL credentials и общей сети с backend/PostgreSQL. |
| Временное и постоянное хранилища разделены | Выполнено: `guest-temporary` и `resumes`, отдельные S3 identities; guest использует условные записи и startup-проверку CAS. Guest health стал healthy после этой проверки. |
| Два vhost и права по операциям | Выполнено в конфигурации: `infra/rabbitmq/init.mjs`, `hr-guest`/`hr-authorized`, quorum queues, отдельные пользователи prepare/evaluate. |
| Короткая оркестрация внутри API | Выполнено: `ProcessingEngine` и consumers events/dead; отдельных dispatcher worker в основном Compose нет. |
| Один общий parser и evaluator для обоих режимов | Выполнено на уровне запущенных сервисов: два контейнера, по два AMQP-соединения на процесс, общий executor с одним вычислительным потоком внутри каждого сервиса. |
| Полная замена прежнего анализатора двумя самостоятельными сервисами | Не завершено: оба образа копируют весь `apps/resume-analyzer/app`, сохраняются прежние точки входа и общий состав зависимостей; см. A-07. |
| Обработчики работают только по job-токенам | Выполнено: проверка RS256, issuer/audience, mode/job/task/file/operation/attempt/deadline и permissions до чтения данных; нет PostgreSQL/S3 credentials. |
| ACK после принятия результата API | Выполнено в исходниках: result API сохраняет результат и подтверждает публикацию события; затем consumer подтверждает команду. |
| Повторы и DLQ выполняет брокер | Выполнено в конфигурации: native delayed retry, delivery-limit=5, DLX; consumers используют basic.reject. |
| Постоянный outbox только у backend | Выполнено: `AuthorizedTaskStore` сохраняет состояние и публикации транзакционно; guest не сканирует S3 для возобновления обработки. |
| TTL, принадлежность задачи, удаление | В основном выполнено; незавершённые загрузки очищаются позже обещанного таймаута, см. A-01. |
| Изоляция рабочих каталогов и исключение из backup | Выполнено в конфигурации и исходниках: TemporaryDirectory, Docker tmpfs, отключён межзаданийный text cache; backup выбирает постоянный bucket и исключает `guest-temporary`. Полное восстановление backup в этой сессии не выполнялось. |
| Доступность обработки отражает готовность модели | Частично: монитор Ollama есть внутри evaluator, но внешний статус учитывает только число AMQP consumers, см. A-02. |
| Единственный владелец смысловой оценки — evaluator | Приложение сохраняет оценки, статусы и факты обработчика; повторная интерпретация цитат при построении отчёта удалена, см. A-06. Корректность стажа внутри evaluator не обеспечена, см. A-05. |

## Найденные расхождения

### A-01 · Средний приоритет: незавершённая загрузка хранится ещё два часа после таймаута

Требование: `docs/guest-task-lifecycle.md`, разделы 4–5 — незавершённая загрузка
по таймауту очищается вместе с записанными частями.

Фактически `expireWork()` переводит uploading в failed и вызывает `finish()`;
тот устанавливает `expires_at = upload_deadline + GUEST_RESULT_TTL_MS`.
`GuestService.cleanup()` пропускает физическое удаление, пока нет `deleted_at`,
а его выставляет только при достижении нового `expires_at`.

Основание: `packages/processing/src/state.ts:33`, `:35`, `:48`;
`apps/guest-api/src/service.ts:74`, `:78`.

Воспроизведение на синтетическом объекте через собранный `@hr/processing`:
создать guest task 11 минут назад, оставить статус uploading, добавить частичный
файл и вызвать `expireWork()`. Получено:

```json
{"status":"failed","deleted":false,"files_remaining":1,"retention_after_upload_deadline_minutes":120}
```

Рекомендация: отдельно закрывать и удалять содержимое просроченной загрузки
после upload timeout, сохраняя только техническую отметку/idempotency-связь.
Добавить проверку фактического удаления S3-объекта при таком исходе.

### A-02 · Средний приоритет: готовность анализа подменена наличием consumer

`apps/backend/src/routes.ts:37` возвращает `available=true`, если в очереди есть
хотя бы один evaluator consumer. `processing_v2/__main__.py:159` аналогично
проверяет в `/health` только оба AMQP-соединения и состояние остановки.
Монитор модели запускается отдельно и не участвует в этом ответе.

Следствие по коду: при недоступной Ollama или отсутствующей модели контейнер
может оставаться healthy, а авторизованный API — сообщать о доступном анализе.
Оценки в это время возвращаются на повторную доставку и могут исчерпать
delivery-limit. Это особенно расходится с `docs/analysis.md:140`, где прямо
сказано, что наличие consumer недостаточно и требуется готовность модели.

Сам по себе отдельный liveness endpoint допустим. Рекомендация: сохранить
liveness и добавить отдельный сигнал readiness модели, который участвует
в прикладном статусе анализа. Проверить это отключением модели в отдельном QA
project. Основную Ollama для воспроизведения этого отказа не останавливали.

### A-03 · Низкий приоритет: инструкции запуска расходятся с текущим Compose

- `docs/analysis.md:7` обещает запуск Ollama обычным `compose up`, но в чистой
  конфигурации требуется профиль `docker-ollama`; далее описаны прежние worker,
  bridge, `/api/analysis/status` и профиль `broker`.
- `docs/architecture.md:7` говорит о поставке обработчиков из другой ветки,
  хотя их Dockerfile и production entrypoint уже находятся в репозитории.
- В локальном `.env` действительно стоял профиль `broker`. Для текущего
  развёртывания исправлено на `processing,docker-ollama`.

Рекомендация: привести документацию к `docs/target-architecture.md` и
`docs/preparation.md`; исторические инструкции явно обозначить как v1.

### A-04 · Низкий приоритет: не все ошибки API получают Cache-Control: no-store

В `apps/frontend/nginx.conf` fallback `location /api/` и `location = /api`
возвращают JSON 404 без `Cache-Control`; обработчик `@too_large` также не
задаёт его. Успешные проксируемые ответы и остальные именованные обработчики
получают `no-store`.

Фактически проверены `GET /api/overview`, `/api/internal/test` и `/api/unknown`:
404, `application/json`, заголовок Cache-Control отсутствует. Требование
`docs/target-architecture.md`, раздел 2: ответы API не кешируются.
Рекомендация: применять `no-store always` также к этим ответам Nginx.

### A-05 · Высокий приоритет: оценщик принимает возраст за релевантный стаж

Статус: **открыт**. В предоставленном `resumes-first-10.pdf` у первого кандидата
Абдрахманова Риназа Рефисовича указано «Мужчина, 23 года»; опыт работы составляет
1 год 5 месяцев, описаны рабочие специальности. Ответ оценщика, воспроизведённый
на этих данных, содержит `status: "met"` и `experience_months: 276` для требования
трёх лет коммерческой разработки Python/Java/Go. Возраст «23 года» попал в цитаты
как подтверждение стажа. Основная оценка — 37,5; диапазон — 37,5–92,5; охват — 45%.

Причина по исходникам: `apps/resume-analyzer/app/evidence_scoring.py`, функции
`duration_months` и `_assess_criterion`. Длительность извлекается из цитаты без
проверки её связи с трудовой деятельностью и требуемой ролью. Проверка наличия
цитаты в исходном тексте сама по себе не доказывает релевантный опыт.

Последствие: синтаксически корректный ответ и цитата из резюме могут обосновывать
неверный статус требования и влиять на балл. Это дефект качества оценки,
который нельзя устранять только оформлением отчёта.

Ответственность за исправление — у evaluator: отличать возраст, образование,
общий и релевантный стаж, связывать длительность с работой и основанием оценки.
Parser отвечает за извлечение содержимого и границы документов; приложение —
за проверку контракта, сохранение и представление результата. По ограничению
пользователя `resume-analyzer` и сервис обработки файлов не изменялись.

Основание воспроизведения: первые три страницы PDF и локальный повтор проверки
`verify_and_score` с контролируемым ответом на их цитатах; артефакты находятся
в исключённом из Git `.qa/report-refinement/`. Это воспроизведение ошибки
проверки evidence, а не новый прогон модели по всем десяти резюме.

### A-06 · Средний приоритет: повторная смысловая оценка при формировании отчёта

Статус: **устранено в приложении; дефект оценщика A-05 открыт**. При доработке
отчётов была добавлена эвристика, которая заново разбирала цитаты оценщика
и исключала возраст из подтверждённого опыта. При этом исходный `score`
сохранялся. Так появлялись два источника смысловых решений: evaluator выставлял
статус и балл, а слой представления менял вывод по критерию независимо от них.
Отображаемое обоснование переставало соответствовать сохранённой оценке.

Эвристика удалена. `packages/contracts/src/rating-report.ts` и компонент
`apps/frontend/src/components/RatingAnalysis.tsx` форматируют переданные статусы,
числа и цитаты без повторной интерпретации стажа. Проверка схемы допустима;
изменение фактов, статусов, штрафов или балла должно происходить в evaluator
с согласованным обновлением всего результата.

Регрессионная проверка: `tests/rating-report-contract.test.ts` подтверждает,
что представление не меняет даже ошибочное утверждение оценщика о 276 месяцах,
его цитату, статус и балл. Следовательно, ошибочный стаж может оставаться виден
до исправления A-05; фронтенд не скрывает противоречие самостоятельным решением.

### A-07 · Высокий приоритет: не завершена замена прежнего анализатора двумя сервисами

Статус: **открыт**. Требование: `docs/target-architecture.md`, разделы об общих
сервисах обработки и разделении обязанностей, и
`docs/processing-services-contract.md`, разделы 1–2. Пользователь подтвердил,
что прежний анализатор должен быть полностью замещён двумя отдельными
сервисами: `resume-parser` для `prepare` и `resume-evaluator` для `evaluate`.

Фактическая организация:

| Элемент | Текущее расположение и запуск |
| --- | --- |
| Разборщик | `apps/resume-analyzer/app/processing_v2/parser.py`, функция `prepare` |
| Оценщик | `apps/resume-analyzer/app/processing_v2/evaluator.py`, функция `evaluate` |
| Общий процесс обработки | `apps/resume-analyzer/app/processing_v2/__main__.py`; роль выбирается через `PROCESSING_OPERATION` |
| Транспорт и проверка задания | `processing_v2/api.py` и `processing_v2/protocol.py` |
| Расчёт оценки | `apps/resume-analyzer/app/scoring.py` и `evidence_scoring.py`, вне `processing_v2` |
| Сборка действующих сервисов | `infra/processing/Dockerfile`, один рецепт с `OPERATION=prepare` или `OPERATION=evaluate` |
| Прежний анализатор | `apps/resume-analyzer/Dockerfile` запускает `app.server`; сохранены `main.py`, `consumer.py`, `pipeline.py` и прежние `job_*` |

Каталогов `apps/resume-parser` и `apps/resume-evaluator` сейчас нет. Основной
Compose действительно запускает два разных контейнера и не запускает прежний
consumer. Однако `infra/processing/Dockerfile:12` копирует **весь** каталог
`apps/resume-analyzer/app` в каждый образ, включая код обеих ролей и прежнего
сервиса. Разные имена образов и значение переменной операции не подтверждают
завершённость разделения исходников и зависимостей.

Выявленные последствия организации:

1. В одном Python-приложении смешаны действующие обработчики, общие функции
   и прежние HTTP/AMQP-точки входа. Название каталога и его собственный Dockerfile
   продолжают указывать на прежний сервис.
2. Существуют параллельные цепочки обработки: прежний
   `pipeline.process_document` использует `resume_document.prepare_resume_document`,
   а новый evaluator самостоятельно извлекает текст, контакты и выполняет оценку.
   Исправление прежнего pipeline не обязательно затрагивает действующий сервис.
3. Оба образа устанавливают общий `apps/resume-analyzer/requirements.txt`,
   включая FastAPI/Uvicorn прежнего HTTP-сервиса, и LibreOffice. Разборщик
   `prepare` не конвертирует DOC и не вызывает модель, но получает эти зависимости
   и сеть `model` через общий шаблон `x-processor` в Compose.
4. `tests/architecture.mjs` проверяет границы импортов TypeScript, но не Python.
   Более того, строки 51–52 закрепляют запуск прежнего `app.server`. Тесты
   `test_processing_v2.py` проверяют работу нового протокола, но отдельной
   проверки границ зависимостей parser/evaluator нет.
5. В Git отслеживается runtime-лог `apps/resume-analyzer/logs/app.log`.
   Генерируемые журналы должны храниться вне исходников и не поставляться
   вместе с приложением.

Необходимое исправление: завершить замену прежнего анализатора двумя сервисами
с собственными точками входа, конфигурациями и составом зависимостей. Общие
функции допустимо вынести в явно выделенные Python-пакеты: транспорт задания,
проверка токенов, работа с документами и определение контактов. Логика требований,
обращения к модели и расчёта балла должна принадлежать evaluator. Parser не должен
зависеть от этой логики. Общий базовый Docker-слой допустим, если итоговый образ
каждого сервиса содержит только нужный ему код и зависимости.

Предлагаемая организация исходников для реализации этого требования:

```text
apps/resume-parser/          # prepare: ZIP и разделение PDF
apps/resume-evaluator/       # evaluate: текст одного резюме, модель и оценка
packages/processing-python/  # общий транспорт и служебный протокол
packages/resume-documents/   # действительно общие функции документов и контактов
```

Это предложение структуры, а не описание уже выполненного переноса. Общий
исходный пакет сам по себе не нарушает границы сервисов; открытый дефект состоит
в незавершённой замене прежнего приложения, неявных зависимостях и сохранении
его альтернативного способа запуска.

Критерии закрытия A-07:

- В штатном развёртывании и документации остаются только parser и evaluator
  как сервисы обработки; у каждого есть собственная точка входа и сборочная цель.
- Нужная логика перенесена из прежнего приложения; его Dockerfile и старые
  HTTP/AMQP-точки входа выведены из эксплуатации и удалены из поставки.
- Итоговые образы не копируют целиком прежнее приложение. Общие пакеты и
  зависимости перечислены явно, parser не импортирует код оценки и модели.
- Parser не получает доступ к сети модели и зависимости, которые не использует.
- Добавлены проверки Python-импортов, независимой сборки обоих образов и
  отсутствия прежнего сервиса в штатной конфигурации; проверки старого запуска
  заменены проверками целевой архитектуры.
- Сохраняются контракты `prepare`/`evaluate`, два режима и vhost, job-токены,
  изоляция временных файлов, подтверждение команды после принятия результата,
  корректная повторная доставка и сценарии ZIP/PDF/одиночного резюме.
- Runtime-логи исключены из Git и из контекста поставки.

Основание: статический разбор исходников, импортов, Dockerfile и Compose,
а также проверка команд запуска действующих контейнеров. В рамках фиксации
