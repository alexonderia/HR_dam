# Необходимые правки по аудиту resume-analyzer — 19 октября 2026

Backend/worker уже подготовлены к восстановлению отдельного резюме; изменения ещё не развёрнуты. Ниже оставшиеся задачи. Контракт API: [описание интеграции](../docs/resume-analyzer-rabbitmq-api.md). Доказательства и результаты предыдущих проверок: [JSON аудита](resume-integration-audit-2026-10-19.json).

## 1. Восстановление одного резюме

**Приоритет: высокий.** Единица повтора — целое резюме. ZIP распаковывается один раз; файлы берутся из S3, требования — из исходного задания. Завершённые документы партии не пересчитываются. Промежуточные оценки профилей должностей сохранять не требуется.

| ID | Файлы в `apps/resume-analyzer/app` | Необходимая правка |
| --- | --- | --- |
| ANR-1 | `consumer.py`, `config.py` | До скачивания, `processing` и вызова модели проверять конкретную попытку через `POST {BACKEND_BASE_URL}/api/internal/resume-jobs/status` с callback Bearer-токеном. Передавать `version`, `job_id`, `batch_id`, `item_id`, `attempt`. При `should_process=true` обрабатывать документ; при false подтверждать старую доставку без расчёта. |
| ANR-2 | `consumer.py`, `job_result.py` | Недоступность backend, Ollama, сети и временный отказ S3 переводить в ожидание с задержкой без увеличения счётчика ошибок документа. Не отправлять `failed` после пяти инфраструктурных повторов. Ожидание не должно блокировать heartbeat Pika. |
| ANR-3 | `consumer.py` | Использовать один управляемый executor. После разрыва AMQP завершать либо кооперативно отменять прежний расчёт перед повторным запуском. Привязать callbacks к исходной сессии: старый callback не должен использовать новое соединение/канал. |
| ANR-4 | `consumer.py`, `rabbitmq_client.py` | Сохранить порядок: persistent result → publisher confirm → ACK входного задания. При отсутствии подтверждения ACK не отправлять. Автоматический повтор сохраняет `job_id`, `batch_id`, `item_id`, `attempt`, файл и snapshot требований; перед расчётом снова выполняется ANR-1. |
| ANR-5 | `consumer.py` | Исправить обращение к `job_id` до присваивания в обработке ошибки валидации. Невалидные сообщения отклонять контролируемо через NACK/DLQ; не допускать бесконечной немедленной повторной доставки. |
| ANR-6 | `consumer.py` | Реализовать SIGTERM: остановить приём новых сообщений, завершить либо кооперативно прервать текущую работу, закрыть канал и executor. Без подтверждённого результата оставлять доставку неподтверждённой. `processing` публиковать после проверки задания и готовности модели. |

Ответ нового API: `{ "status": "completed", "should_process": false }`.

- `pending` / `processing`, true — разрешён расчёт всего резюме, включая восстановление прерванного запуска.
- `completed` / `failed` / `superseded`, false — ACK старой доставки без расчёта.
- Сетевой отказ и 5xx — ожидать и повторять проверку; они не разрешают начинать расчёт.
- 401/422 — ошибка конфигурации/контракта, 404 — неизвестное задание: диагностировать и отклонять контролируемо, без бесконечного requeue.

Проверяется именно `job_id` и попытка, а не общий статус кандидата: новая переоценка ранее завершённого резюме должна выполняться. Метод не резервирует задание; повторная запись результатов остаётся идемпотентной на стороне backend. Ручной повтор создаёт новый `job_id` и следующую `attempt`.

**Критерии приёмки:**

1. В ZIP три документа: первый сохранён, второй обрабатывается, третий ожидает. После перезапуска consumer либо тестового RabbitMQ с сохранённым томом пересчитывается второй, затем третий; первый не запускается снова, дубликатов в БД нет.
2. Соединение оборвано после publisher confirm, но до ACK: повторная доставка безопасна; при уже сохранённой квитанции БД модель не вызывается. Если результат ещё в пути, повторный расчёт допустим, повторная запись — нет.
3. Ollama/backend/S3 недоступны дольше пяти интервалов retry: документ остаётся ожидающим и после восстановления завершается в той же попытке. Повреждённый документ завершается ошибкой без бесконечных повторов.
4. Старое задание после ручного повтора/замены резюме пропускается; новая переоценка completed-кандидата выполняется.

## 2. Достоверность оценок

**Приоритет: высокий.** Файлы: `scoring.py`, `rank_models.py`, `analysis_service.py`; при расширении результата — контракты и валидация backend.

- Для утверждений о навыках, опыте и образовании требовать подтверждение фрагментом исходного текста. Не переносить требования вакансии в `matched_keywords` автоматически.
- Связывать сработавшие стоп-факторы с входным списком. Если он пуст, `triggered_stop_factors` должен быть пустым. Другие пробелы отражать отдельно в объяснении.
- Разделить «подтверждено», «не соответствует» и «сведения отсутствуют/требуют уточнения». Не считать отсутствие сведений доказанным отсутствием компетенции.
- Формировать объяснение из проверенных сравнений. Исключить противоречия между найденными навыками и текстом объяснения, а также требования, которых нет в задании.
- Согласовать воспроизводимые правила score: веса требований, частичное соответствие, влияние стажа и стоп-факторов. Проверить качество на независимой разметке рекрутеров.

**Регрессии:** у Мироновой не должны появляться неподтверждённые Python/Pandas/Tableau/Power BI и frontend-навыки; у Москаленко объяснение должно явно учитывать 1 год 3 месяца при требовании от трёх лет. Правильный итоговый балл определяется согласованной формулой.

## 3. ФИО и телефон

**Приоритет: средний.** Файлы: `candidate_extractor.py`, `job_processor.py`; общий путь HTTP/AMQP и сохранение контактов — также backend/worker.

- Объединять строки ФИО, корректно обрабатывать фамилию на отдельной строке и перенос отчества. Добавить признаки уверенности и источник полей, исключить распознавание заголовков как имени.
- Использовать одно извлечение контактов для HTTP и AMQP. HTTP-путь должен передавать контакты принимающей стороне, а не только оценки.
- Добавить восстановление контактов старых записей без повторного скоринга; обычная переоценка с `target_resume_id` сейчас их не обновляет.
- Явно обрабатывать неподдерживаемые номера и отсутствие текста. OCR и международные номера реализовывать после согласования необходимого охвата.

**Критерий приёмки:** отчество Румянцевой «Константиновна» извлекается со следующей строки; отсутствие отчества в исходнике остаётся `null`. Старые ручные контакты не перезаписываются автоматически.

## 4. Готовность, конфигурация и общий сервис

**Приоритет: средний.** Файлы: `consumer.py`, `main.py`, `readiness.py`, `config.py`, `job_processor.py`, `docker-compose.yml`, `/api/analysis/status` в backend.

- Разделить liveness, подключение к брокеру, готовность модели и занятость. Backend должен получать реальную готовность native analyzer; наличие consumer в очереди недостаточно. Добавить healthcheck consumer.
- Запретить одновременное потребление одной очереди native consumer и HTTP bridge.
- Унифицировать модель по умолчанию, таймауты, timezone, readiness и logging. В consumer подключить общую настройку логов.
- Передавать `analysis_duration_ms` явно для выполненного анализа, исключая ожидание очереди и инфраструктурных повторов.
- Объединить обработку документа, контактов и ошибок для HTTP/AMQP в общий pipeline. Для текущей установки достаточно одного analyzer-сервиса с явным выбором адаптера `http|amqp`; при объединении обеспечить управляемый lifecycle и общий ограничитель обращений к модели. Несколько процессов потребуют отдельной координации.

**Критерии приёмки:** при недоступной модели API сообщает ожидание, задания не становятся failed из-за инфраструктуры; конфигурация с native+bridge отвергается; режимы одинаково извлекают контакты и формируют итоговый результат.

## 5. Применение изменений

1. Выполнить ANR-1–ANR-6 и проверки восстановления на отдельной тестовой БД/vhost; не останавливать рабочий брокер ради испытаний.
2. Проверить совместимость нового status API, повторной доставки и итогового контракта. Перезапускать только незавершённые документы с исходными требованиями.
3. Собрать и пересоздать backend/worker и доработанный analyzer. Не считать восстановление native завершённым до совместного развёртывания и прохождения приёмочных сценариев.
