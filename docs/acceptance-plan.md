# План проверки пункта 8

Дата: 10 ноября 2026 года. Проверяем текущую реализацию после подключения
разборщика и оценщика и исправления готовности модели.

Это план будущего прогона. Прошлые успешные тесты служат основанием для выбора
сценариев, но не заменяют итоговую проверку текущего кода.

## Порядок и правила выполнения

Выполняем блоки 0–9 по порядку. Найденный дефект исправляем, повторяем его
сценарий и связанные проверки. Отмечаем результат: PASS, FAIL или НЕ ПРОВЕРЕНО.
Для FAIL сохраняем способ воспроизведения, ожидаемый и фактический результат.

Основное приложение на порту 3000 содержит существующие данные. Остановки
сервисов, изменение сроков задач, подмену токенов и повреждённые входы проверяем
в отдельном Compose project с собственными сетями и volumes. Для тестовых
кандидатов используем синтетические или обезличенные документы.

Два существующих стенда запускаются последовательно:

| Стенд | Назначение | Адрес |
| --- | --- | --- |
| `hr-dam-processing-qa` | API, права, очередь, сбои и интерфейс; синтетические обработчики | `http://localhost:13000` |
| `hr-dam-processors-qa` | Настоящие процессы разборщика и оценщика; тестовый ответ модели | `http://localhost:13100` |

Для настоящей Ollama и ClamAV потребуется отдельный QA overlay: существующие
QA-конфигурации используют заменители. Подготовка этого overlay входит в блок 4.
Зелёный тест с заменителем не доказывает качество модели или работу антивируса.

## 0. Зафиксировать исходное состояние

**Как:** записать commit, список локальных изменений, версии/ID работающих
образов, модель Ollama, её настройки и состояние миграций. Проверить доступность
Docker и Ollama. Для основного стенда проверить наличие актуальной резервной
копии, не перезаписывая данные. Выбрать контрольные существующие резюме и сохранить
их технические ID и контрольные суммы оценок для итогового сравнения.

Подготовить набор документов с заранее известным содержимым:

- Одиночные PDF, DOCX, DOC, RTF и TXT.
- Пакет из пяти резюме; ZIP с вложенными каталогами; PDF одного кандидата
  и сборный PDF с продолжениями страниц.
- Резюме без телефона, без образования, с подтверждённым стоп-фактором.
- Пустой/повреждённый файл, скан без текста, PDF с неоднозначными границами.
- Архив с исправными и ошибочными элементами; архив с запрещённым путём,
  превышением лимитов или шифрованием.

**Прошло, если:** окружения разделены; известны ожидаемые кандидаты, страницы,
контакты и факты для каждого файла. Пароли, cookie и содержимое резюме не
попадают в публикуемые артефакты.

## 1. Сборка и автоматические проверки кода

**Как:** из корня проекта с установленными зависимостями выполнить:

```bash
npm run build
npm test
npm run test:architecture
npm run test:compose
git diff --check
```

Python-проверки выполнять в окружении образа оценщика, где установлены его
зависимости. Команда для текущего локального запуска на Mac:

```bash
docker compose --profile processing \
  -f docker-compose.yml \
  -f docker-compose.local-ollama.yml \
  -f docker-compose.mac.yml \
  run --rm --no-deps \
  -e PYTHONPATH=/app:/tests \
  -e TEXT_CACHE_MAX_ITEMS=0 -e TEXT_CACHE_MAX_BYTES=0 \
  -v "$PWD/apps/resume-analyzer/tests:/tests:ro" \
  --entrypoint python resume-evaluator \
  -m unittest test_readiness test_service_runtime test_processing_v2
```

Перед командой убедиться, что образ собран из проверяемого кода. Этот запуск
проверяет функции в отдельном контейнере, не запускает consumer и не отправляет
задания в основной брокер.

**Прошло, если:** сборка и все тесты завершились успешно. В частности, проходят
пять долгих заданий подряд с виртуальным временем, проверка настоящей
недоступности модели и восстановление после таймаута.

## 2. API, авторизация и очередь в изолированном стенде

**Как:** запустить готовый сценарий:

```bash
python3 tests/run_processing.py
```

Нужны Docker, зависимости Node.js и Chrome для браузерной части. Скрипт
использует project `hr-dam-processing-qa`, синтетические документы и обработчики;
останавливает сервисы только этого project. Сохранить вывод и браузерные
артефакты из `.qa/processing`.

Проверить по результатам сценария: вход/выход/обновление сессии, изоляцию гостя,
сохранение результатов сотрудника, условную запись S3, повтор POST без дублей,
доставку через RabbitMQ, частичный отчёт, восстановление outbox и удаление.

**Прошло, если:** все проверки завершились PASS. Отдельно отметить пропуски:
существующий сценарий не покрывает автоматически весь последующий список.

После сохранения артефактов остановить только этот стенд: скрипт сам его не убирает.

```bash
docker compose -p hr-dam-processing-qa \
  -f docker-compose.yml -f tests/compose.processing.yml down
```

## 3. Настоящие разборщик и оценщик с предсказуемой моделью

**Как:** запустить:

```bash
python3 tests/run_processors.py
```

Сценарий собирает образы, использует project `hr-dam-processors-qa`, проверяет
гостя при выключенных backend/PostgreSQL, затем сохранение результата сотрудника.
В конце удаляет контейнеры/сети этого стенда, сохраняя его volumes.

Дополнить проверками из набора блока 0, которых нет в готовом сценарии:

| Проверка | Ожидаемый результат |
| --- | --- |
| Одиночные поддерживаемые форматы | Текст извлечён; выдан один результат на резюме |
| ZIP с несколькими резюме | Число заданий оценки совпадает с числом пригодных резюме |
| Сборный PDF | Верное число кандидатов и страниц; продолжения не становятся отдельными кандидатами |
| Смешанный ZIP | Пригодные резюме обработаны; ошибки остальных видны; отчёт частичный |
| Скан, пустой PDF, неоднозначные границы | Понятная конечная ошибка, без бесконечных повторов |
| Опасный путь, шифрование, превышение лимитов | Вход отклонён; файлы не выходят за рабочий каталог |
| Повтор команды или результата | Сохраняется один результат, не появляются дубли кандидатов/файлов |

**Прошло, если:** все пригодные документы разобраны правильно, ошибки
изолированы по файлам и отрабатывают согласно контракту.

## 4. Настоящая модель, антивирус и последовательная обработка

**Как:** подготовить отдельный QA overlay для штатного ClamAV и локальной Ollama,
с отдельными именами контейнеров, портом и volumes. Убедиться, что проверяется
та же модель и настройки, что используются основным приложением.

Через интерфейс выполнить в режиме сотрудника и гостя:

1. Загрузить одно резюме и проверить полный путь до сохранённого результата.
2. Загрузить пять резюме подряд одним пакетом, затем повторить пакет после
   завершения с новым заданием. Время хотя бы одного анализа должно превысить
   срок свежести проверки модели — сейчас 35 секунд.
3. При одновременных гостевом и авторизованном заданиях проверить отсутствие
   смешивания кандидатов, критериев и результатов.
4. Проверить отклонение стандартного тестового образца EICAR настоящим ClamAV;
   при недоступном антивирусе новая загрузка должна завершиться понятной ошибкой.

**Прошло, если:** каждый пакет из пяти пригодных файлов завершён без потери
заданий; оценки сохранены; нет ложной недоступности после долгого анализа.
Результаты гостя не появляются в постоянной БД. Антивирусные проверки используют
именно штатный ClamAV.

## 5. Качество извлечения и оценок

**Как:** взять не менее десяти разных обезличенных резюме. До запуска вручную
составить ожидаемые факты, контакты, границы кандидатов и соответствие критериям.
Включить явное соответствие, явное несоответствие, недостаток сведений и
подтверждённый стоп-фактор. Сопоставить ответы модели с оригиналами.

Проверять по каждому результату:

- ФИО и телефон не перепутаны с другими людьми и не выдуманы.
- Утверждения и приведённые подтверждения опираются на текст резюме.
- Отсутствующие сведения обозначены как неизвестные.
- Все заданные профили оценены по снимку требований соответствующего задания.
- Баллы и стоп-факторы рассчитаны согласно политике evidence-v1.
- Объяснение в карточке и отчёте соответствует сохранённым данным.

**Прошло, если:** нет перепутанных кандидатов, выдуманных контактов и
подтверждений; расчёт по политике корректен. По неоднозначным требованиям
составлен список расхождений и принято решение по каждому. Срок обработки
измерен и укладывается в настроенный deadline. Одинаковый балл в повторных
ответах модели сам по себе не является условием прохождения.

## 6. Сбои, перезапуски и сохранность заданий

**Как:** в QA для каждого сценария создавать отдельное задание и записывать его
ID. Отключать только указанный сервис; после проверки возвращать его в работу.

| Сценарий | Что должно произойти |
| --- | --- |
| Оценщик выключен, разборщик работает | Подготовленные резюме остаются в очереди; после запуска оценщика продолжают обработку |
| Ollama недоступна и возвращается | Ограниченные повторы через RabbitMQ; при восстановлении в пределах попыток/deadline задача завершается |
| Лимит доставок исчерпан | Задание получает конечную ошибку; другие файлы сохраняют результаты; для сотрудника доступен штатный повтор |
| Перезапуск backend и брокера | Принятая авторизованная задача сохранена; outbox допубликовывает команды; нет дублей |
| Перезапуск обработчика во время анализа | Неподтверждённая доставка возвращается в очередь; сохранённый результат повторно не создаётся |
| S3 недоступно, затем восстановлено | Ошибка не маскируется под успех; доступные файлы и состояния сохраняются; итог соответствует лимитам повторов |
| Перезапуск SeaweedFS | Все контрольные файлы по-прежнему читаются через S3; размер и SHA-256 совпадают; последующая обработка работает |
| Нет маршрута / потерян confirm | Нет ложного подтверждения приёма; авторизованный outbox восстанавливает неподтверждённые действия |
| Повтор/запоздалый результат старой попытки | Первый допустимый результат сохранён; устаревшая попытка не заменяет текущую |
| Истёк deadline гостя | Готовая часть доступна до срока хранения, остальные этапы конечные; прежняя задача не возобновляется, новая отправка возможна |

Для RabbitMQ отдельно зафиксировать реальный интервал повторных доставок,
рост delivery-count при basic.reject, попадание в DLQ и приём HTTP result до ACK.
Для потерянного confirm/negative confirm использовать контролируемый сбой
в QA; если готовый тест не создаёт нужное условие, добавить отдельный сценарий.

**Прошло, если:** нет исчезнувших принятых авторизованных задач, дублей и
бесконечно зависших состояний; файлы после перезапуска хранилища проходят SHA-256.

## 7. Границы доступа и изоляция

**Как:** использовать две независимые гостевые сессии и сотрудника.
Проверять HTTP-ответы, реальные права брокера/S3 и конфигурацию сетей.

- Без входа `/api/app/*`, скачивание и экспорт постоянных данных закрыты.
- Старые URL, `/internal/*` и проверочные location Nginx недоступны извне.
- Поддельная, истёкшая и отозванная сессии не открывают данные. Проверить Origin.
- При отключённом auth-check запросы блокируются с JSON-ошибкой; `/health`
  Nginx остаётся доступным. Тело загрузки не передаётся в auth-check.
- Гость A не читает, не скачивает и не удаляет задачи гостя B; авторизованный
  клиент не может использовать гостевые endpoints с действующей сессией сотрудника.
- Подмена job_id/file_id/mode/operation/attempt, issuer/audience и срока токена
  отклоняется; evaluate не загружает выходные файлы; prepare не читает чужие файлы.
- Гостевой job-токен отклоняется авторизованным API до обращения к БД.
- Гостевой API не обращается к постоянному bucket/БД и авторизованному vhost.
  Обработчики читают только очередь своей операции и не публикуют команды.
- Гостевая обработка настоящими worker-процессами завершается при выключенных
  PostgreSQL и backend; у обработчиков нет доступов и сетей хранилищ.
- Каталоги разных заданий разделены, после операции очищены; кеш не переносит
  содержимое между заданиями и режимами.

**Прошло, если:** каждый отрицательный тест получает ожидаемый отказ без
раскрытия данных; неизвестные ID не приводят к поиску в другом режиме.

## 8. Интерфейс, бизнес-сценарии и очистка

**Как:** проверить в браузере на ширине 1280 и 390 пикселей, включая
перезагрузку страницы во время обработки. Сопоставить интерфейс с ответами API.

| Проверка | Ожидаемый результат |
| --- | --- |
| Гость: очередь допуска → загрузка → анализ → отчёт | Стадии различимы; до входа нет запросов к API сотрудника |
| Вход, выход, истечение сессии | Режим переключается корректно; прежние данные сотрудника убираются из клиентского состояния |
| Пакет и частичная ошибка | Числа источников/кандидатов/готовых/ошибок верны; готовая часть доступна |
| Обновление страницы и краткий отказ API | Состояние восстанавливается из сервера; сбой опроса не удаляет готовые результаты |
| Повтор одного неудачного файла | Готовые результаты остальных файлов не меняются |
| Кандидаты и требования | Проверены дубли, замена резюме, защищённый статус «В процессе», чёрный список, изменение профиля и повторная оценка |
| Скачивание, экспорт, печать | Файлы открываются; данные и фильтры соответствуют выбранному отчёту |
| Удаление гостевой задачи | Доступ закрыт сразу; поздний результат не возвращает данные |
| Истечение срока | API закрывает доступ независимо от задержки физического удаления |
| Физическая очистка | Файлы, критерии и результаты удалены; остаётся только допустимая техническая отметка до абсолютного срока |
| Сбой очистки и повторный проход | Очистка продолжается после восстановления; постоянные файлы сохранены |

Ускорять время и сроки только в QA. Отдельно проверить брошенную загрузку,
частично записанные объекты и отсутствие гостевого bucket в постоянных backup.

**Прошло, если:** сценарии завершены без ошибок JavaScript и скрытых зависаний,
временные данные действительно удаляются, контрольные постоянные записи и оценки
не изменились.

## 9. Итоговая приёмка

Составить отчёт `reports/acceptance-YYYY-MM-DD.md`: проверяемый commit и локальные
изменения, образы/модель, сценарии PASS/FAIL/НЕ ПРОВЕРЕНО, исправления, логи без
секретов, снимки интерфейса, замеры времени и список известных ограничений.

Пункт 8 закрывается, когда:

- Все обязательные сценарии пройдены на текущем коде и реальных образах.
- Нет потери или раскрытия данных, смешивания кандидатов, дублей от повторов
  и необъяснимых зависаний. Критичные и существенные дефекты устранены.
- Реальная Ollama и ClamAV проверены отдельно от заменителей.
- Успешные старые результаты и постоянные файлы сохранились.
- Ограничения OCR/сложных PDF и найденные ограничения качества явно описаны.
- Для перехода с v1 проверено отсутствие незавершённых старых заданий до
  отключения прежнего worker/rank bridge. Если переход уже выполнен, это
  подтверждено отдельно.

Подготовка к публичному серверу с HTTPS и развёртывание в него выполняются
отдельно: итог локальной проверки сам по себе не означает публикацию приложения.
