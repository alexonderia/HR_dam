# Целевая архитектура обработки резюме и контракт resume-analyzer

## Поток обработки

1. Фронтенд отправляет одиночное резюме или ZIP без обязательного указания кандидатов. Backend проверяет файлы, распаковывает архив и отправляет отдельное задание на каждый документ в `hr.resume.storage`.
2. Worker сохраняет документ в S3 и только после успешной записи публикует задание со ссылкой на файл в `hr.resume.analysis`.
3. Resume-analyzer получает задание, скачивает документ, извлекает данные кандидата и оценивает резюме. Начало обработки отправляет в `hr.resume.progress`, результат или ошибку — в `hr.resume.results`.
4. Backend последовательно принимает результаты. В одной транзакции создаёт или находит кандидата, сохраняет резюме, ссылку на S3 и рейтинги, проверяет чёрный список. Фронтенд обновляет список и счётчики.

RabbitMQ передаёт JSON-сообщения. Распаковку, запись в S3 и работу с БД выполняют backend/worker. Бинарные документы через RabbitMQ не передаются. Одиночная загрузка и повторная оценка используют тот же поток.

Список файлов и события обработки хранятся в очередях RabbitMQ; успешная обработка подтверждается записями в БД. `pending_files = total_files - processed_files - failed_files`. Новые таблицы и поля для прогресса не нужны. ФИО и телефон кандидата допускают `null`.

## Обязанности resume-analyzer

- AMQP consumer очереди `hr.resume.analysis` и publisher для прогресса и результатов.
- Скачивание PDF, DOCX, DOC, RTF, TXT из S3 по подписанной ссылке, проверку размера и SHA-256; обновление истёкшей ссылки через backend.
- Извлечение текста, фамилии, имени, отчества и телефона с источниками и уверенностью полей. Отсутствующие данные возвращать как `null`; поддерживаемые номера из 11 цифр с префиксом `+7`, `7` или `8` нормализуются в `+7…`. Для остальных форматов возвращаются `null` и статус `unsupported`; OCR и международное автоизвлечение не включены.
- Анализ по снимку `requirements` из задания: одна оценка для каждого переданного профиля, без пропусков, дубликатов и посторонних UUID.
- Подтверждения доставки, обработку повторных заданий и ошибок по правилам ниже. Запись кандидатов, рейтингов и проверку чёрного списка выполняет backend.

Нативный AMQP consumer уже реализован. Оставшиеся доработки восстановления описаны в [аудите 19 октября](../reports/resume-integration-audit-2026-10-19.md#1-восстановление-одного-резюме). Собственный HTTP endpoint для получения заданий ему не требуется: задания поступают через AMQP.

## AMQP API

В Compose: `rabbitmq:5672`, vhost `/`, учётные данные `RABBITMQ_USER` / `RABBITMQ_PASSWORD`. Для внешнего analyzer нужен доступный адрес брокера и S3. Очереди объявляет приложение. Exchange: `""`, routing key: имя очереди. Сообщения: JSON UTF-8, `content_type=application/json`, `delivery_mode=2`; очереди durable.

| Очередь | Направление | Назначение |
| --- | --- | --- |
| `hr.resume.analysis` | worker → resume-analyzer | Задание анализа одного документа |
| `hr.resume.progress` | resume-analyzer → backend | Начало обработки документа |
| `hr.resume.results` | resume-analyzer → backend | Успешный результат или ошибка |

Analyzer не потребляет служебные очереди `hr.resume.storage`, `hr.resume.batch.*`, `*.retry`, `hr.resume.dead`.

### Общие поля всех сообщений

```json
{
  "version": 1,
  "job_id": "a0000000-0000-4000-8000-000000000001",
  "batch_id": "b0000000-0000-4000-8000-000000000001",
  "item_id": "a0000000-0000-4000-8000-000000000001",
  "attempt": 1
}
```

`job_id` — идентификатор попытки, `batch_id` — загрузки, `item_id` — документа; `attempt` — номер попытки от 1 до 100. Analyzer копирует их из задания без изменений. При ручном повторе backend меняет `job_id` и увеличивает `attempt`; при повторной доставке брокером значения сохраняются. AMQP `correlation_id` рекомендуется равным `job_id`.

**Каждый JSON ниже — дополнение к общим полям. В RabbitMQ отправляется один объект: общие поля вместе с указанным содержимым.**

### Вход: `hr.resume.analysis`

```json
{
  "file": {
    "id": "a0000000-0000-4000-8000-000000000001",
    "file_id": "f0000000-0000-4000-8000-000000000001",
    "source_path": "folder/resume.pdf",
    "file_name": "resume.pdf",
    "mime_type": "application/pdf",
    "size_bytes": 12345,
    "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
    "bucket": "resumes",
    "object_key": "resume-imports/resume.pdf",
    "download_url": "http://seaweedfs:8333/resumes/resume-imports/resume.pdf?X-Amz-Signature=example",
    "download_url_expires_at": "2026-10-16T12:00:00.000Z",
    "candidate_hint": { "last_name": null, "first_name": null, "middle_name": null, "phone": null }
  },
  "requirements": [{
    "id": "c0000000-0000-4000-8000-000000000001",
    "name": "ИТ", "track": "it", "comment": "", "is_active": true,
    "profiles": [{
      "id": "d0000000-0000-4000-8000-000000000001",
      "cluster_id": "c0000000-0000-4000-8000-000000000001",
      "position_name": "Разработчик", "education": "", "experience": "",
      "keywords": ["Python"], "stop_factors": [], "comment": "", "is_active": true
    }]
  }]
}
```

`file.id` соответствует документу загрузки, `file.file_id` — записи файла. `candidate_hint` содержит необязательные данные из формы; `candidate_hint_source=manual` и `manual_contact_fields` указывают введённые вручную поля. Для повторной оценки используются `candidate_hint_source=snapshot`, `manual_contact_fields=[]`, `file.target_resume_id` и `file.target_updated_at`: такой снимок не считается новым ручным вводом. Это правило действует и для старых заданий с `target_resume_id` без явного источника. Возвращать эти поля в результате не нужно. Требования из задания нельзя заменять актуальными настройками из БД.

### Выход: успешный результат в `hr.resume.results`

```json
{
  "status": "completed",
  "candidate": { "last_name": "Иванов", "first_name": "Иван", "middle_name": null, "phone": "+79991234567" },
  "contact_details": {
    "version": 1, "method": "rules-ru-v1", "text_status": "present",
    "name_status": "extracted", "phone_status": "extracted",
    "fields": {
      "last_name": { "source": "resume_text", "confidence": "high", "quote": "Иванов Иван", "line_start": 1, "line_end": 1 },
      "first_name": { "source": "resume_text", "confidence": "high", "quote": "Иванов Иван", "line_start": 1, "line_end": 1 },
      "middle_name": null,
      "phone": { "source": "resume_text", "confidence": "high", "quote": "+7 (999) 123-45-67", "line_start": 2, "line_end": 2 }
    },
    "warnings": []
  },
  "analysis": { "clusters": [{
    "id": "c0000000-0000-4000-8000-000000000001",
    "profiles": [{
      "id": "d0000000-0000-4000-8000-000000000001", "score": 82,
      "matched_keywords": ["Python"], "triggered_stop_factors": [],
      "details": {}, "explanation": "Опыт соответствует требованиям."
    }]
  }] }
}
```

Обязательны `candidate`, `analysis`, UUID кластеров/профилей и `score` от 0 до 100. Поля внутри `candidate` допускают `null` или отсутствие. `matched_keywords`, `triggered_stop_factors`, `details`, `explanation` необязательны. Не добавляйте в результат исходные `file`, `requirements` и другие поля вне схемы.

Текущий анализатор возвращает `contact_details` с цитатами, номерами строк с единицы и уверенностью `high`/`medium`. Каждое непустое поле `candidate` должно иметь источник с цитатой, содержащей это значение; у отсутствующего поля источник равен `null`. Автоматически сохраняются только поля с высокой уверенностью. Для совместимости принимаются старые результаты без `contact_details`, но они не исправляют существующие контакты. Заполненные старые поля без источника и ручные значения защищены; отсутствие значения в тексте не удаляет сохранённое поле. Формат и восстановление без оценки описаны в [contact-extraction.md](contact-extraction.md).

В методе `evidence-v1` поле `score` — нижняя подтверждённая граница, а `details.score_range` содержит `{ "min": 0, "max": 100 }` с учётом неизвестных сведений. `details` содержит версию предварительно согласованной формулы, охват критериев, проверенные цитаты с границами в Unicode code points, статусы `met/partial/not_met/unknown`, веса и штрафы. Backend проверяет эти поля относительно исходных требований и повторяет расчёт. Формула и ограничения описаны в [scoring-policy.md](scoring-policy.md). Число без диапазона не следует трактовать как точный процент компетенций кандидата.

### Выход: ошибка в `hr.resume.results`

В успешном результате и ошибке можно передать `analysis_duration_ms` — целое число от 0 до 2147483647, длительность анализа в миллисекундах без ожидания в очереди. При отсутствии поля backend вычисляет время по событию `processing` этой же попытки. Длительность сохраняется в истории загрузки и событиях резюме; в результатах оценок показано время последней успешной оценки.

```json
{
  "status": "failed",
  "error": { "code": "TEXT_EXTRACTION_FAILED", "message": "Не удалось извлечь текст документа." }
}
```

`code` — до 100 символов, `message` — до 2000, без трассировок и секретов. Ошибка отображается сотруднику; кандидат и резюме для неуспешного импорта не создаются.

Если из документа извлечено меньше 50 символов после удаления пробелов по краям, analyzer возвращает `TEXT_EXTRACTION_FAILED` без автоматического повтора и вызова модели для оценки. Сообщение: «Не удалось извлечь достаточно текста из резюме. Загрузите документ с доступным текстом.» HTTP `/rank` для такого документа возвращает 422 с тем же сообщением в `detail`.

### Выход: начало обработки в `hr.resume.progress`

```json
{
  "stage": "processing",
  "created_at": "2026-10-16T11:00:00.000Z"
}
```

Отправляйте после готовности приступить к анализу. Analyzer публикует только `processing`; остальные состояния формирует приложение.

### Доставка и повторы

- Единица задания — один документ, а не ZIP и не отдельный профиль должности. После сбоя допускается пересчёт всего незавершённого резюме; уже сохранённые документы партии не пересчитываются. Промежуточные оценки профилей передавать не требуется.
- Использовать manual ACK и `prefetch=1` на consumer. Результат публиковать persistent-сообщением, дождаться publisher confirm, затем подтвердить входное задание. Для результата `message_id=job_id`, для прогресса — `job_id:processing`.
- Повторная доставка допустима; backend применяет успешный результат идемпотентно по `job_id`, подтверждая сообщение после сохранения в БД. Результаты устаревших ручных попыток игнорируются.
- Временная недоступность модели или сети требует ожидания/повтора с задержкой. Не запускать немедленный бесконечный NACK/requeue. Невосстановимую ошибку документа возвращать как `status=failed`.
- Автоматический повтор сохраняет исходные `job_id`, `batch_id`, `item_id`, `attempt` и snapshot требований. Новый ручной запуск получает новый `job_id` и следующую `attempt`.
- Backend/worker не расходуют `hr-retries` на распознанные временные отказы БД, хранилища и транспорта. HTTP bridge также ожидает после HTTP 429/503 и временных сетевых ошибок. Аналогичное поведение для Ollama в нативном Python consumer ещё нужно реализовать.
- Время обработки должно укладываться в настроенный acknowledgement timeout брокера.

## Вспомогательный HTTP API backend

Перед повторным расчётом проверить конкретную попытку:

```http
POST /api/internal/resume-jobs/status
Authorization: Bearer <RESUME_ANALYZER_CALLBACK_TOKEN>
Content-Type: application/json

{
  "version": 1,
  "job_id": "a0000000-0000-4000-8000-000000000001",
  "batch_id": "b0000000-0000-4000-8000-000000000001",
  "item_id": "a0000000-0000-4000-8000-000000000001",
  "attempt": 1
}
```

Ответ 200: `{ "status": "completed", "should_process": false }`.

| status | should_process | Действие consumer |
| --- | --- | --- |
| `pending` / `processing` | `true` | Обработать резюме целиком. `processing` допускает восстановление прерванного запуска. |
| `completed` | `false` | Результат этого job_id уже в БД; подтвердить доставку без нового расчёта. |
| `failed` | `false` | Попытка завершилась ошибкой; подтвердить старую доставку. Ручной повтор создаёт другую попытку. |
| `superseded` | `false` | Новая попытка или версия резюме заменила эту; подтвердить старую доставку. |

401 — неверный токен, 422 — неверная оболочка, 404 — неизвестная партия/документ. При временной недоступности backend/БД/RabbitMQ возвращается 503; сетевой отказ/5xx означает ожидание и повтор проверки, а не ошибку документа и не разрешение начать расчёт. Запрос использует только поля оболочки; `file` и `requirements` не передаются.

Backend проверяет принадлежность документа манифесту, актуальность `job_id`/`attempt`, квитанцию `scored` и версию существующего резюме. `completed` возвращается по сохранённой квитанции даже до публикации финального события прогресса. Статус кандидата `completed` от предыдущей оценки не отменяет новое задание. Метод не резервирует задание и не является распределённой блокировкой: повторная доставка результатов по-прежнему должна быть идемпотентной.

Нативный consumer вызывает этот метод перед обработкой. Worker storage и HTTP bridge используют ту же проверку напрямую через data-access.

Для обновления истёкшей ссылки (срок — один час):

```http
POST /api/internal/resume-imports/{batch_id}/items/{item_id}/download-url
Authorization: Bearer <RESUME_ANALYZER_CALLBACK_TOKEN>
```

В Compose базовый адрес — `http://backend:3001`. Ответ 200: `{ "download_url": "...", "download_url_expires_at": "..." }`; 401 — неверный токен, 404 — неизвестный документ, 409 — файл ещё не сохранён. Hostname подписанной ссылки менять нельзя.

Вместо прямой AMQP-публикации доступны `POST /api/internal/resume-results` и `POST /api/internal/resume-progress`: те же полные тела сообщений и Bearer-токен; ответ 202 после публикации в RabbitMQ. Получение заданий остаётся через AMQP.

## Режимы приложения и подключение analyzer

Значения задаются в корневом `.env` одинаково для backend и worker:

| `ANALYZER_ADAPTER` | `RABBITMQ_ENABLED` | `RANK_BRIDGE_ENABLED` | Обработка |
| --- | --- | --- | --- |
| `http` | `false` | `true` | Очередь в постоянном томе → S3 → HTTP `/rank` |
| `http` | `true` | `true` | RabbitMQ → HTTP bridge → RabbitMQ |
| `amqp` | `true` | `false` | RabbitMQ → native consumer внутри сервиса resume-analyzer |

Native + bridge и AMQP без брокера отклоняются при старте. Consumer очереди анализа эксклюзивный в обоих адаптерах: второй потребитель не подключится даже при разном окружении контейнеров. В режиме `amqp` HTTP `/rank` отключён с 409, `/health`, `/status`, `/ready` и `/contacts` остаются доступны.

После изменения переменных остановите backend/worker и пересоздайте контейнеры:

```powershell
docker compose stop backend worker
docker compose --profile broker up -d --build --remove-orphans --wait
```

Для режима без брокера вторую команду замените на `docker compose up -d --build --wait`, затем остановите RabbitMQ: `docker compose stop rabbitmq`. Обычный `restart` не обновляет окружение. Незавершённые задания между режимами автоматически не переносятся; сначала завершите их в исходном режиме.

Нативный consumer запускается в lifespan единственного `resume-analyzer` при `ANALYZER_ADAPTER=amqp`; отдельный сервис `resume-analyzer-consumer` удалён. При первом обновлении `--remove-orphans` удаляет прежний контейнер consumer. Для локальной Ollama используйте те же параметры `-f docker-compose.yml -f docker-compose.local-ollama.yml`, что и при исходном запуске. HTTP и AMQP используют один pipeline и возвращают одинаковые контакты, оценки и безопасные ошибки. Успешный результат явно содержит `analysis_duration_ms` без времени ожидания и инфраструктурных повторов. Оба адаптера используют одну модель, таймауты, часовой пояс Москвы и настройку логирования.

HTTP `/contacts` принимает только multipart-поле `file` и возвращает `candidate` и `contact_details` без оценки и проверки готовности модели. Backend использует его для просмотра и восстановления контактов старого резюме. При отсутствии текста возвращаются пустые контакты и `text_status=no_text`; `/rank` отклоняет такой документ с 422. Восстановление не меняет оценки и не запускает скоринг.

Точные схемы сообщений: [imports.ts](../packages/contracts/src/imports.ts); формат рейтингов: [domain.ts](../packages/contracts/src/domain.ts).
