# Гостевое задание и временное хранение

Дата: 6 ноября 2026 года. Статус на 9 ноября: реализовано в guest-api; проверено с синтетическими обработчиками обработки.

Документы: [архитектура](target-architecture.md), [контракты сервисов](processing-services-contract.md), [план реализации](implementation-plan.md).

## 1. Сохраняемые данные

| Данные | Где |
| --- | --- |
| ID задачи, хэш идентификатора гостевой сессии, статусы и ID заданий, deadline обработки, время создания и удаления | JSON-объект состояния в bucket `guest-temporary` |
| Критерии и полученные оценки | JSON-объекты этой же задачи в `guest-temporary` |
| Исходники и реально выделенные файлы резюме | Bucket `guest-temporary` |
| Допуск к загрузке и связь Idempotency-Key с задачей | Временные технические JSON-объекты в том же bucket |
| Команды и события, ожидающие доставки обработчикам | Гостевой vhost RabbitMQ; ID/технические поля, в заголовке команды — токен её задания |

Готовые файлы резюме содержат ссылку на исходник и, для PDF, исходные страницы. Отчёт формируется из результатов оценок.

В PostgreSQL нет гостевых схем, записей, сессий или очереди допуска. Guest API использует только временное объектное хранилище и гостевой RabbitMQ. Consumers событий/DLQ и процедура очистки работают внутри guest-api; отдельного guest-worker нет. Контур не подключает модули бизнес-данных и не обращается к API авторизованного режима.

Разборщик и оценщик общие для обоих режимов. Для гостевой команды они получают job-токен, действующий только на её исходник, выходы и результат через Guest API. Он не принимается авторизованным API. Принадлежность и права Guest API проверяет по токену и собственному временному состоянию; общим сервисам не выдаются PostgreSQL/S3 credentials или универсальные API-токены.

## 2. Работа пользователя

1. Заполнить критерии и выбрать файлы.
2. Получить допуск к загрузке. При перегрузке ждать без передачи содержимого; неиспользованное разрешение истекает.
3. Отправить файлы и критерии одним запросом через Nginx после проверки доступа через auth_request. Guest API сохраняет источники и состояние, публикует `task.accepted` и возвращает 202 с ID только после подтверждения RabbitMQ и маршрутизации в очередь. Если публикация не подтверждена, возвращается ошибка.
4. Получать статус и готовые оценки по HTTP. Закрытие вкладки не отменяет обработку. Возобновление незавершённой задачи после сбоя не гарантируется; при конечной ошибке пользователь отправляет файлы заново.
5. Просмотреть или скачать отчёт до указанного срока. Удалить данные раньше по кнопке.

Гостевая сессия создаётся guest-api и идентифицируется подписанной cookie с непредсказуемым идентификатором и сроком, без серверной таблицы сессий. Cookie проверяется локально и действует не меньше срока доступности её задач. Принадлежность задачи проверяется по хэшу идентификатора в её состоянии, вместе со сроком; одного UUID недостаточно. Cookie имеет HttpOnly и SameSite=Lax; в локальной среде HTTP — Secure=false, на рабочем сервере с HTTPS — Secure=true. Изменяющие запросы защищены проверкой Origin/CSRF. После refresh текущий результат загружается с сервера. Перенос доступа между браузерами не предусмотрен.

## 3. API

Nginx допускает эти маршруты только в гостевой контур после auth_request с политикой guest. Auth-check проверяет cookie авторизации без БД и доступа к данным задач, гостевую cookie и принадлежность задачи проверяет сам guest-api. `/api/app/*` без авторизации отклоняется на Nginx до обращения к backend; внутренние маршруты и проверочные location не публикуются. Guest API не проксирует запросы по произвольному пути, bucket, object key или URL. ID постоянного файла, кандидата или профиля не является допустимым входом гостевого API. Неизвестная или чужая задача возвращает 404 без сведений о её владельце.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/guest/queue` | Встать в очередь допуска, передав число файлов и заявленный объём |
| `GET /api/guest/queue/:id` | Получить состояние ожидания или краткоживущее разрешение загрузки |
| `POST /api/guest/tasks` | Отправить разрешение, критерии и файлы; после сохранения получить `202` с task_id |
| `GET /api/guest/tasks/:id` | Статус, счётчики, ошибки, готовые оценки и срок удаления |
| `GET /api/guest/tasks/:id/report` | Отчёт по доступным результатам |
| `GET /api/guest/tasks/:id/download` | Скачать отчёт |
| `DELETE /api/guest/tasks/:id` | Закрыть доступ и запустить удаление |

Очередь допуска содержит только технические записи. Принадлежность записи и разрешения проверяется по гостевой сессии; разрешение привязано к одной отправке и имеет срок. Резервирование и освобождение допуска сохраняются с проверкой версии, после сбоя неиспользованный допуск освобождается по таймауту. Файлы и критерии отправляются после допуска. Заявленный размер не заменяет проверку фактических байтов и распакованного объёма.

POST tasks использует Idempotency-Key, который frontend сохраняет на время отправки. Ключ привязан к гостевой сессии и задаче во временном хранилище. В пределах срока задачи повтор после потери ответа возвращает её текущее состояние. Он не восстанавливает неотправленную или завершившуюся ошибкой задачу и не запускает обработку заново. Повтор с изменёнными файлами/критериями отклоняется с 409; для новой отправки нужен новый ключ.

### Запись состояния и сообщения RabbitMQ

Каждая задача имеет собственный префикс объектов; ключи формируются сервером. Критерии и результаты записываются отдельно от файлов. JSON-состояние содержит ссылки на них и назначенные job_id для защиты от дубликатов. Журнала ожидающих публикации команд и сканирования задач для возобновления нет. Только готовые и проверенные входы переводятся в queued.

Создание технического объекта требует условной записи «только если отсутствует», изменение — атомарного сравнения сохранённой версии/ETag. При конфликте обработчики API повторно читают состояние и проверяют срок, задание и допустимость перехода. Обычная последовательность GET → безусловный PUT не допускается: она может потерять параллельную оценку или отменить удаление. Эта защита нужна и без восстановления после сбоев. Семантика условной записи описана в [документации S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html); её атомарность на выбранном SeaweedFS проверяется конкурентным интеграционным тестом до включения гостевого режима.

RabbitMQ хранит и доставляет `task.accepted`, команды prepare/evaluate и события результатов. Consumers внутри guest-api формируют команды из списка источников или выделенных резюме и делают ACK события после сохранения состояния и подтверждения всех публикаций. HTTP-приёмник результата сохраняет JSON и публикует событие результата с подтверждением; только затем возвращает успех внешнему сервису. Брокер выполняет повторы с задержкой и ограничивает число доставок. Подробности — в [контракте](processing-services-contract.md).

Специальное восстановление после сбоя для гостя не реализуется: нет outbox, повторного запуска по записям S3 и обещания продолжить незавершённый процесс после рестарта. Durable-очереди и штатная повторная доставка RabbitMQ используются; повтор не создаёт вторую оценку или файл. Сбой на границе S3 и публикации может завершить гостевую задачу ошибкой. Пользователь создаёт новую отправку.

## 4. Статусы и ошибки

Задача имеет состояния `uploading`, `queued`, `processing`, `completed`, `partially_completed`, `failed`. Техническая запись uploading создаётся до сохранения файлов; обработка начинается только после готовности всех входов. Незавершённая загрузка по таймауту очищается вместе с записанными частями. У каждого файла свой статус и ошибка. Счётчики исходников и найденных резюме различаются.

Если файл нельзя прочитать или разделить на отдельных кандидатов, ошибка показывается в отчёте. Пользователь может исправить источник и создать новую задачу.

Временную ошибку consumer возвращает брокеру через basic.reject с requeue=true; native delayed retry и delivery-limit задаются в RabbitMQ. Постоянная ошибка файла завершается сразу. Повтор сохраняет job_id/attempt, счётчик неудачных доставок ведёт брокер. После исчерпания лимита DLQ-consumer API фиксирует конечную ошибку. Отсутствующая или удаляемая задача не создаётся ответом обработчика заново.

При принятии задачи устанавливается deadline обработки: минимум из времени принятия плюс настроенный лимит обработки и абсолютного срока created_at + 24 часа. Если к нему часть этапов не завершена, они считаются неуспешными; задача получает failed либо partially_completed при наличии готовых оценок. API фиксирует этот исход при чтении статуса или очистке, без запуска восстановления. Поздние сообщения больше не применяются.

## 5. Срок хранения

- При создании устанавливается абсолютный срок: `created_at + 24 часа`.
- После завершения срок удаления: `min(finished_at + 2 часа, created_at + 24 часа)`.
- Незавершённые загрузки имеют ограниченный таймаут и также очищаются.
- Чтение статуса, скачивание и повтор обработки не продлевают абсолютный срок.

finished_at выставляется один раз после конечного исхода completed/partially_completed/failed. Для незавершённой к deadline обработки задачи конечным временем считается этот deadline, а не более позднее время чтения статуса. При достижении абсолютного срока прекращаются также ещё не законченные задания. Сроки хранения и таймаут загрузки задаются конфигурацией приложения.

Срок доступности возвращается в API и отображается пользователю. До него разрешены повторные скачивания. Первое скачивание не удаляет задачу автоматически.

## 6. Удаление

По сроку или DELETE guest-api закрывает доступ к задаче и приём результатов. Проверка выполняется на каждом публичном и внутреннем запросе, даже если очистка ещё не удалила объекты. Для недоступной своей задачи API возвращает 410, после удаления её технической отметки — 404. DELETE возвращает 202 только после сохранения отметки удаления: доступ закрыт, физическое удаление выполняет ограниченная фоновая процедура guest-api.

Процедура очистки удаляет исходники, выделенные резюме, критерии, оценки и состояние задачи. До её абсолютного срока остаётся только техническая отметка удаления и связь ключа повторной отправки, чтобы запоздалый POST не создал задачу заново; пользовательского содержимого в отметке нет. Отсутствующий объект считается уже удалённым. Неудачная очистка повторяется после запуска API: отказ от восстановления обработки не отменяет удаление гостевых данных. Ошибка очистки должна быть видна оператору.

Поздняя загрузка результата повторно проверяет существование задачи, срок и задание перед сохранением ссылки. Если задача недоступна, файл не регистрируется и удаляется. События закрытой задачи и сообщения её DLQ подтверждаются без выполнения и без создания состояния. Периодическая уборка обрабатывает оставшиеся после незавершённой загрузки или сбоя записи файлы. TTL сообщений RabbitMQ не удаляет объекты S3.

Общие разборщик и оценщик создают отдельный каталог/контекст для каждого задания, удаляют его после операции и очищают оставшееся после перезапуска. Содержимое заданий разных режимов не переносится между обработками. Эти обязанности входят в общий контракт сервисов приложения.

Временный bucket и рабочие каталоги не входят в резервные копии. Содержимое резюме, критериев и отчётов не записывается в логи. Удаление гостевых данных не имеет доступа к постоянному bucket и базе авторизованного режима.
