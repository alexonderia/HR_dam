# Архитектура приложения

Рабочая схема описана в [целевой архитектуре](target-architecture.md). Здесь
показано, где она реализована. Для запуска см. [подготовку окружения](preparation.md),
для гостевых данных — [жизненный цикл](guest-task-lifecycle.md).

| Каталог | Ответственность |
| --- | --- |
| `apps/frontend` | React, статические ресурсы и Nginx. Публичные маршруты, ограничения загрузки и проверка доступа через auth_request. |
| `apps/auth-check` | Локальная проверка подписи сессии и определение режима. |
| `apps/guest-api` | Допуск, загрузка, отчёты и очистка. Состояние и файлы находятся в отдельном временном bucket. |
| `apps/backend` | Учётные записи, PostgreSQL, постоянное хранилище, бизнес-правила и транзакционный outbox. |
| `apps/resume-parser`, `apps/resume-evaluator` | Самостоятельные сервисы prepare и evaluate с отдельными образами и requirements. |
| `packages/contracts` | Типы и схемы обмена, проверка результатов и общие правила отображения отчётов. |
| `packages/security`, `packages/processing` | Подписи и сессии, общий движок событий, внутренний API, доступ к S3 и RabbitMQ. |
| `packages/data-access`, `packages/documents` | Доступ к постоянным данным и работа с документами на стороне Node.js. |
| `packages/processing-python`, `packages/resume-documents` | Общий транспорт Python и функции чтения документов. |
| `db/migrations`, `infra`, `tests` | SQL-миграции, сборка и инфраструктура, проверки приложения. |

Nginx отправляет запросы `/api/guest/*` в guest-api, `/api/app/*` и
`/api/auth/*` в backend, `/api/session` в auth-check. Backend повторно
проверяет подписанную cookie и серверную сессию. Guest API проверяет
принадлежность временной задачи по гостевой сессии.

Оба API публикуют команды и подтверждают результаты внутри своего RabbitMQ
vhost. Обработчики читают файл и сохраняют результат через внутренний API по
токену задания. При принятии оценки API проверяет контракт и согласованность
балла. Для старых отчётов действует отдельное правило отображения
неподтверждённых дополнительных выводов. Оно описано в
[политике оценки](scoring-policy.md) и сохраняет исходные результаты.

Образы auth-check, guest-api и backend собираются через `infra/node/Dockerfile`
с аргументом `SERVICE`. Frontend имеет собственный Dockerfile и зависит
только от `@hr/contracts` среди внутренних пакетов. Node-сборка ведётся через
npm workspaces с общим lockfile и `install-strategy=nested`.

Backend читает ранее сохранённые результаты из PostgreSQL. Если у существующей
оценки нет снимка требований, перед изменением кластера или профиля backend
сохраняет исходное состояние требований для следующих сравнений.

Текущие проверки и команды запуска перечислены в [README](../README.md#обработка).
