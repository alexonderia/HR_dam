# План реализации

Дата: 6 ноября 2026 года. Статус на 9 ноября: подготовка приложения реализована; раздел 5 выполняется в другой ветке. Проверки с реальными образами — после объединения.

Основание: [архитектура](target-architecture.md), [гостевые данные](guest-task-lifecycle.md), [контракт разборщика и оценщика](processing-services-contract.md).

Результат подготовки и проверки: [отчёт от 9 ноября](../reports/application-preparation-2026-11-09.md).
Запуск и подключение образов другой ветки: [инструкция по запуску](preparation.md).

План охватывает всё приложение. Разборщик и оценщик реализует другой участник команды в отдельной ветке этого репозитория; остальные части разрабатываются параллельно по общим контрактам. Реализация обоих сервисов и их интеграция входят в общий план.

## 1. Контракты

Общие задачи команды:

1. Зафиксировать команды prepare/evaluate и события task.accepted, prepare.completed/failed, evaluate.completed/failed; порядок publisher confirms/ACK, ошибки и delivery policies из контракта.
2. Добавить схемы проверки сообщений в `packages/contracts` и подготовить тестовые файлы без персональных данных.
3. Зафиксировать `/api/guest/*`, `/api/app/*`, `/api/session`, проверку через Nginx/auth-check, раздельные внутренние API и vhost. Описать права общих обработчиков и job-токены: claims, permissions, заголовок x-job-token, ключи API и проверки перед доступом к данным.
4. Реализовать получение исходника, загрузку готового резюме и возврат оценки отдельно в guest-api и backend.
5. Для проверки интеграции использовать тестовые ответы сервисов до поставки реальных образов.

Условие завершения: компоненты могут разрабатываться в отдельных ветках по общему протоколу с явно разделёнными доступами.

## 2. Nginx, проверка сессии и авторизованный контур

1. Переработать существующий `apps/frontend/nginx.conf`: заменить общее проксирование `/api/*` явными маршрутами из [архитектуры](target-architecture.md). Nginx остаётся единственным публичным входом. Проверить наличие `http_auth_request_module` в образе и валидность конфигурации через `nginx -V`/`nginx -t`.
2. Реализовать внутренний auth-check с `/verify` и `/session`: проверка подписи, алгоритма, назначения, издателя и срока токена по открытому ключу, без PostgreSQL dependencies, бизнес-кода и внешних запросов. `/verify` применяет политику guest/authorized и возвращает 204/401/403; `/session` возвращает режим для frontend и сбрасывает недействительную cookie.
3. Настроить в Nginx внутренние `/__auth_guest` и `/__auth_app` с auth_request: передавать только cookie и необходимые заголовки, не тело файла; служебную политику задавать конфигурацией. `GET /api/session` проксировать в auth-check/session. Проверку доступа не кешировать; при отказе отдавать JSON 401/403, при недоступности проверки — 503 без передачи запроса в API.
4. На backend реализовать вход/выход/обновление серверной сессии и выдачу короткоживущей подписанной cookie. Перед постоянными операциями backend сам проверяет токен и действующую серверную сессию; не доверяет клиентским заголовкам идентификации. При отзыве/истечении серверной сессии возвращать 401 и сбрасывать cookie.
5. Перенести существующие API кандидатов, кластеров, профилей, файлов, чёрного списка, экспорта и статусов обработки под `/api/app/*`. Старые публичные URL закрыть без алиасов; `/internal/*`, прежние `/api/internal/*` и проверочные location не публиковать. Сохранить публичный health Nginx без опроса БД и внутренних сервисов.
6. Отклонять `/api/app/*` без авторизации до обращения к backend, `/api/guest/*` с действующей авторизацией — с 403. Перезаписывать заголовки внутренней идентификации; не использовать поля запроса для выбора прав и не перенаправлять ошибочный запрос в другой контур. Закрыть прямой публичный доступ к API, auth-check, хранилищам и обработчикам.
7. Предусмотреть локальный запуск на `http://localhost:3000` без TLS-сертификатов: HttpOnly, SameSite=Lax и Secure=false только для локального HTTP. На рабочем сервере — HTTPS и Secure=true. Настроить Origin/CSRF, запрет кеширования ответов API, лимиты и потоковые загрузки `proxy_request_buffering off`/`proxy_http_version 1.1`; ошибки API не подменять frontend HTML.
8. Сохранить общую базу авторизованного режима и текущие правила кандидатов, замен резюме и статусов. Новые миграции нужны только для авторизации и авторизованного режима; применённые V1–V5 не менять.

Условие завершения: Nginx направляет запросы только в разрешённый контур; прямые ссылки и прежние маршруты не открывают постоянные данные. Определение режима не обращается к БД. Локальная разработка работает через HTTP без сертификатов.

## 3. Временные гостевые данные

1. Добавить отдельный guest-api с consumers событий/DLQ и ограниченной процедурой очистки внутри этого процесса. Не выдавать ему PostgreSQL credentials, доступ к сети БД, постоянному bucket и API авторизованного контура. Не импортировать `@hr/data-access`; выделить необходимые S3/AMQP-адаптеры без PostgreSQL и бизнес-репозиториев.
2. Добавить bucket `guest-temporary` с отдельными ограниченными credentials. В нём хранить исходники, готовые резюме и JSON-состояние задач, критериев, результатов, допуска и ключей повторной отправки. Outbox, журнала неотправленных команд, гостевых миграций и схемы PostgreSQL нет.
3. Реализовать условное создание и атомарное обновление технических объектов с проверкой версии. Подтвердить конкурентным тестом на развёрнутом SeaweedFS, что две записи с одной ожидаемой версией не могут обе завершиться успешно; одного наличия заголовка If-Match недостаточно. Поддержка этой семантики хранилищем обязательна до включения гостевого режима.
4. Создавать состояние uploading перед сохранением файлов; принимать файлы/критерии потоком, проверять размер/тип/антивирус. После сохранения входов публиковать task.accepted с publisher confirms/mandatory и возвращать 202 только после подтверждения. При сбое публикации возвращать ошибку без обязательства восстановить задачу. Idempotency-Key возвращает прежнее состояние, но не запускает прерванную обработку заново; изменённое содержимое требует нового ключа. Незавершённые загрузки очищаются по таймауту.
5. Реализовать очередь допуска перед загрузкой с ограничением активных запросов. Её техническое состояние хранить в гостевом bucket; ожидающие клиенты не передают файлы заранее.
6. Реализовать подписанную гостевую cookie без таблицы сессий; срок должен покрывать доступность задач. На чтении задачи/отчёта, скачивании и удалении проверять принадлежность и срок только по гостевому состоянию. Не принимать ссылки на постоянные файлы/профили и произвольные storage URL.

Условие завершения: гостевой сценарий работает при выключенных PostgreSQL и авторизованном backend, без восстановления прерванных задач. Файлы и состояние находятся вне RAM; сохранённые результаты доступны после refresh, закрытие вкладки само по себе не отменяет обработку. Сбой может завершить её ошибкой с возможностью новой отправки.

## 4. Оркестрация через RabbitMQ

1. Из `apps/backend/src/imports.ts` убрать собственную распаковку архива; он обслуживает только авторизованный режим и берёт критерии из профилей. Guest API принимает критерии только из формы и не вызывает imports.ts или import-results.ts.
2. Зафиксировать RabbitMQ версии 4.3+ и настроить hr-guest/hr-authorized, exchanges команд/событий/DLX и quorum queues из контракта. У каждого API права только в своём vhost; у общего разборщика чтение prepare в обоих, у общего оценщика — evaluate в обоих, без права публикации. Для prepare/evaluate/events задать native delayed retry, delivery-limit, consumer-timeout, ограничения объёма и at-least-once DLX с overflow=reject-publish. Отдельные очереди на пользователей/задачи не создавать.
3. В API каждого контура добавить consumers событий. Task.accepted создаёт prepare/evaluate по источникам, prepare.completed — evaluate по готовым файлам; остальные события обновляют результаты и конечный статус. Задания имеют стабильные ID, повтор события не создаёт новые сущности. Consumer делает ACK после сохранения состояния и подтверждения всех производных публикаций.
4. Каждый API выпускает job-токены для назначенных команд по контракту. Свою пару ключей API хранит отдельно от пользовательской авторизации; обработчикам передаются только открытые ключи. Внутренние endpoints сначала проверяют токен и его права, затем читают только своё задание. POST result сохраняет результат и возвращает успех после подтверждения completed/failed брокером; сервис затем делает ACK команды. В AMQP передавать ID/технические поля и x-job-token в заголовке команды; файлы/критерии/результаты остаются вне брокера, токены не попадают в события или логи.
5. Внешние consumers при временной ошибке используют basic.reject(requeue=true), чтобы брокер увеличивал delivery-count и выполнял backoff; постоянную ошибку документа передают как failed и делают ACK после принятия API. API не назначает повторы отдельными таймерами. Consumers DLQ фиксируют конечную ошибку, не изменяют завершённый исход и не создают отсутствующие/удалённые задачи.
6. Для гостя не реализовывать outbox, сканирование S3 для перезапуска обработки или обязательное восстановление после сбоев. В авторизованном backend сохранять состояние и намерения публикации транзакционно и повторно отправлять неподтверждённое после сбоя; эта короткая фоновая процедура работает внутри backend. Принятые сообщения обоих контуров обслуживает RabbitMQ.
7. Гостевые результаты сохранять только в `guest-temporary`; для авторизованного режима использовать текущие бизнес-правила. Проверять issuer/audience, mode, operation, file_id, current job_id/attempt, deadline и конечное состояние. Гостевой job-токен на авторизованном API отклонять до запроса в PostgreSQL. Токен evaluate не допускает загрузку выходных файлов; prepare ограничен исходником и выходами своего задания. При неизвестном ID не искать данные в другом контуре.
8. Собирать общий статус и частичный отчёт по готовым оценкам. Для гостя при достижении deadline оставшиеся этапы завершать ошибкой без повторного запуска. Фоновые consumers и очистку ограничить по параллелизму, чтобы они не вытесняли HTTP-загрузки и скачивания.

Условие завершения: маршрутизация, доставка, ожидание повторов и исчерпание доставок выполняются RabbitMQ; отдельного worker-диспетчера нет. Код приложения сохраняет результаты и формирует производные команды. Восстановление неотправленных действий требуется только авторизованному контуру.

## 5. Разборщик и оценщик

Раздел работ другого участника команды, выполняемый в его ветке:

| Сервис | Реализация сервиса | Интеграция с API контура задания и RabbitMQ |
| --- | --- | --- |
| Разборщик | Распаковку ZIP, определение границ резюме в PDF, выделение готовых файлов, происхождение/страницы и ошибки | Команду prepare, доступ к источнику и приём выходных файлов |
| Оценщик | Чтение одного резюме, сведения о кандидате, оценки и объяснения по критериям | Команду evaluate, файл, снимок критериев и приём результата |

Запускаются два контейнера обработки: один общий разборщик и один общий оценщик для обоих режимов. Каждый читает свою операцию через отдельные соединения с двумя vhost и обращается к разрешённому API по job-токену из команды. У них нет PostgreSQL/S3 credentials, универсального API-токена и ключей выпуска job-токенов. Реализация включает алгоритмы, проверку токена/очереди, разрешённые адреса API, manual ACK/basic.reject, deadline и health endpoint из [контракта](processing-services-contract.md). Каталоги и контекст разделяются по job_id и очищаются после операции; содержимое не переносится между заданиями. Общий параллелизм учитывает оба vhost. Сервисы не вызывают друг друга и не публикуют команды; задержки повторов задаёт брокер. Реализацию выполняет назначенный участник команды в своей ветке.

Условие завершения: реальные образы проходят примеры входов/выходов и ошибок из [контракта](processing-services-contract.md).

## 6. Frontend

1. Перед выбором режима вызывать `/api/session` через Nginx. В гостевом режиме монтировать только гостевой экран и обращаться только к `/api/guest/*`; существующий DataProvider и запросы `/api/app/*` запускать после подтверждения авторизации.
2. Добавить гостевую форму образования, опыта, навыков, стоп-факторов и комментария с выбором одного/нескольких файлов или архива.
3. Показать ожидание допуска, загрузку и обработку как разные состояния.
4. Опросом HTTP получать статусы, готовые оценки и ошибки. Различать число загруженных источников и найденных кандидатов.
5. Показать соответствие каждому критерию, неизвестные сведения, стоп-факторы и объяснение. Добавить скачивание, срок доступности и удаление.
6. Оставить текущие экраны авторизованного режима после входа; при выходе и 401 очищать их клиентское состояние и кеши, заново запрашивать `/api/session`. Не переключать и не повторять неуспешную отправку автоматически между API режимов.
7. Для гостевой задачи после сбоя или deadline показывать готовую часть отчёта и ошибку; предлагать новую отправку без обещания возобновить прежнюю.

Условие завершения: гость получает отчёт без доступа к постоянной базе, сотрудник сохраняет текущие возможности приложения.

## 7. Очистка и эксплуатация

1. В guest-api добавить ограниченную процедуру удаления по сроку: до 2 часов после конечного исхода, но не более 24 часов с создания. finished_at устанавливается один раз, для незавершённой к deadline задачи равен deadline. API закрывает доступ независимо от задержки физической очистки; TTL сообщений RabbitMQ не заменяет удаление файлов.
2. Удалять гостевые файлы, критерии, оценки, состояние, незавершённые загрузки и оставшиеся после сбоев объекты. Минимальную отметку удаления и связь Idempotency-Key хранить до абсолютного срока задачи, затем удалять. Неудачную очистку повторять.
3. Проверять существование задачи и текущую попытку при записи результата, чтобы поздний ответ не возвращал удалённые данные.
4. Исключить временный bucket, гостевые рабочие файлы и временные файлы буферизации Nginx из backup. Текущие scripts/backup_common.py и scripts/s3_snapshot.mjs сохраняют public и настроенный постоянный S3_BUCKET; гостевых данных в PostgreSQL нет. Не писать пользовательское содержимое, cookie и токены в логи.
5. Подключить auth-check, guest-api, один общий разборщик и один общий оценщик в Compose; consumers событий работают внутри API. Использовать существующий Nginx, убрать зависимость его старта от backend и сохранить разрешение имён Compose во время работы. Guest API имеет только гостевые доступы; общие обработчики подключаются к обоим vhost и внутренним API, но не к сетям PostgreSQL/S3, и получают только AMQP credentials и открытые ключи проверки. Закрытые ключи job-токенов остаются в соответствующем API. Запуск frontend/auth-check/гостевой обработки не зависит от PostgreSQL/backend. После старых заданий отключить worker и rank bridge. Настроить наблюдение за очередями, DLQ и очисткой.

Условие завершения: временные данные действительно удаляются, а постоянные записи и их резервные копии сохраняют прежнюю работу.

## 8. Проверка и включение

- Проверить одиночное резюме, несколько файлов, ZIP, PDF одного кандидата и сборный PDF.
- Проверить ошибку разбора, отсутствующие сведения, недоступный оценщик и частичный результат.
- Проверить публикацию в отсутствующий маршрут, negative/missing confirm, порядок ACK, повтор команды/события, basic.reject/delivery-count, native backoff и DLQ на зафиксированной версии RabbitMQ. Проверить fan-out N файлов без зависимости разборщика от оценщика.
- Для авторизованного режима проверить сохранность принятой задачи, восстановление неподтверждённых действий после рестарта backend и отклонение устаревшей попытки. Для гостя проверить допустимый конечный исход failed/partially_completed по deadline без восстановления и возможность новой отправки.
- Проверить гостевую сессию, доступ без авторизации, повтор POST после потери ответа без запуска заново, брошенную загрузку, скачивание до срока и запрет после срока даже при задержке очистки.
- Проверить гостевой сценарий через общие обработчики при остановленных PostgreSQL и backend. У guest-api/auth-check нет прав к постоянной БД; у разборщика/оценщика вообще нет PostgreSQL/S3 credentials и соответствующих сетей. Для гостевой операции не выполняются обращения к авторизованному backend или БД, в коде гостевого API/auth-check/обработчиков нет импортов модулей бизнес-БД.
- Проверить Nginx/auth_request для отсутствующей, действующей, поддельной и истёкшей cookie; отзыв серверной сессии, сброс cookie через `/api/session` и backend, недоступность auth-check, запрет прямого вызова проверочных location и отсутствие передачи тела файла в проверку. Проверить HTTP на localhost, потоковую загрузку и JSON-ошибки без подмены HTML.
- Для каждого постоянного endpoint, скачивания и экспорта проверить отсутствие доступа без входа, через старый URL, подмену заголовков, mode/user_id, cookie, ID и токена callback. Неизвестные/чужие гостевые ID не раскрывают данные других задач.
- Проверить права RabbitMQ: Guest API не читает/пишет авторизованный vhost; общий разборщик читает только prepare обоих режимов, оценщик — только evaluate; оба не публикуют команды. Проверить job-токены: чужие issuer/audience/job_id/file_id/operation, срок, подмену mode, запрет output для evaluate и запрет пользовательского API.
