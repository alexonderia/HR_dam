# Контракт разборщика и оценщика

Обновлено: 9 ноября 2026 года.
API приложения уже реализован. Разборщик и оценщик разрабатываются в другой ветке по этому контракту.

## 1. Границы сервисов

| Сервис | Что получает | Что возвращает | За что не отвечает |
| --- | --- | --- | --- |
| Разборщик (`prepare`) | Один архив или PDF | Отдельные файлы резюме и сведения об их происхождении | Не оценивает кандидатов, не получает критерии, не запускает оценщик |
| Оценщик (`evaluate`) | Одно резюме и готовый набор требований | Сведения о кандидате, оценки и объяснения | Не распаковывает архивы, не разделяет сборные PDF, не выбирает профили |
| API приложения | Исходные файлы, требования и результаты обработчиков | Задания обработки и итоговый отчёт | Не выполняет алгоритмы разбора и оценки |

API управляет последовательностью: принимает исходник → назначает разбор при необходимости → назначает оценку каждого резюме → собирает результат. Обычный одиночный файл может сразу поступить оценщику.

**Обработчики получают задания из RabbitMQ, а файлы и результаты передают через HTTP API. События в RabbitMQ публикует API приложения. Обработчики ничего не публикуют в RabbitMQ и не вызывают друг друга.**

## 2. Отделение от остальных частей приложения

- Разборщик и оценщик — два самостоятельных сервиса с отдельными образами. Каждый обслуживает и гостевой, и авторизованный режим, но сохраняет отдельный контекст каждого задания.
- У обработчиков нет доступа к PostgreSQL и S3: нет соответствующих паролей, ключей и сетевых подключений. Файлы доступны только через API текущего задания.
- Разборщик читает только очереди разбора, оценщик — только очереди оценки. Создание очередей, публикация сообщений и чтение чужих очередей запрещены.
- Внутренний API принимает подписанный токен конкретного задания. Пароль сотрудника и браузерная сессия для него не используются. Обработчики получают только открытые ключи проверки токенов.
- Гостевое задание работает через Guest API; авторизованное — через backend. Адрес выбирается из настроек сервиса после проверки задания. Произвольные адреса из сообщения не принимаются.
- Критерии передаются только оценщику. Для гостя их формирует Guest API из формы, для сотрудника — backend из сохранённых профилей. Обработчики сами не читают кандидатов, профили или чёрный список.
- Для задания выделяется отдельный временный каталог. После завершения или ошибки файлы удаляются. Содержимое резюме, критерии и токены не записываются в логи и не переносятся между заданиями.

Каждый сервис предоставляет `GET /health`. Параметры запуска, ключи и подключение образов описаны в [инструкции по запуску](preparation.md).

## 3. Контракт с RabbitMQ

Используется AMQP 0.9.1. Обработчик открывает отдельное соединение для каждого режима через `GUEST_AMQP_URL` и `AUTHORIZED_AMQP_URL`.

| Режим | Пространство RabbitMQ | Очередь разборщика | Очередь оценщика |
| --- | --- | --- | --- |
| Гостевой | `hr-guest` | `hr.guest.prepare` | `hr.guest.evaluate` |
| Авторизованный | `hr-authorized` | `hr.authorized.prepare` | `hr.authorized.evaluate` |

API публикует команды в обменник `hr.processing`. Ключ маршрутизации — `<mode>.<operation>`, например `guest.prepare` или `authorized.evaluate`. Топологию создаёт приложение; обработчик только подписывается на свою очередь с ручным подтверждением.

Обе операции получают одну форму сообщения — JSON в UTF-8:

```json
{
  "job_id": "10000000-0000-4000-8000-000000000001",
  "task_id": "20000000-0000-4000-8000-000000000001",
  "file_id": "30000000-0000-4000-8000-000000000001",
  "operation": "prepare",
  "mode": "guest",
  "attempt": 1,
  "deadline": "2026-11-10T12:00:00.000Z"
}
```

| Поле | Значение |
| --- | --- |
| `job_id` | UUID операции |
| `task_id` | UUID всей пользовательской задачи |
| `file_id` | UUID входного файла операции |
| `operation` | `prepare` — разбор; `evaluate` — оценка |
| `mode` | `guest` — гость; `authorized` — сотрудник |
| `attempt` | Номер попытки приложения, целое от 1 до 100 |
| `deadline` | Крайний срок обработки в ISO 8601 с часовым поясом |

Все поля обязательны, дополнительные поля в JSON запрещены. Идентификаторы и дата в примере иллюстративные.

Свойства AMQP: `content_type=application/json`, `delivery_mode=2`, `message_id=job_id`. Заголовок `x-job-token` содержит токен задания. Файлов, критериев и адресов для скачивания в сообщении нет.

Обработчик сверяет режим и операцию с очередью, проверяет подпись токена и соответствие его полей заданию. При повторной доставке `job_id` и `attempt` не меняются: счётчик доставок RabbitMQ не является новой попыткой приложения.

## 4. Контракт с HTTP API

| Режим | Настройка адреса | Адрес в Compose |
| --- | --- | --- |
| Гостевой | `GUEST_API_BASE_URL` | `http://guest-api:3002/internal/guest` |
| Авторизованный | `AUTHORIZED_API_BASE_URL` | `http://backend:3001/internal/app` |

Пути ниже добавляются к адресу выбранного API. Каждый запрос содержит `Authorization: Bearer <токен из x-job-token>`.

| Метод и путь | Запрос | Успешный ответ |
| --- | --- | --- |
| `GET /jobs/:job_id/input` | Без тела | `job_id`, `attempt`, `should_process`, `file`, `limits`; для оценки также `requirements.targets` |
| `GET /jobs/:job_id/files/:file_id` | Без тела | Байты входного файла |
| `PUT /jobs/:job_id/output/:file_key` | Один файл `file` и JSON-поле `metadata` в multipart/form-data; только для разборщика | `file_id`, `size_bytes`, `sha256` |
| `POST /jobs/:job_id/progress` | JSON: `job_id`, `attempt`, `status: "processing"` | `200 {"accepted":true}` |
| `POST /jobs/:job_id/result` | JSON результата из раздела 5 | `200 {"accepted":true}` после сохранения результата и подтверждения публикации его события |

`file` содержит `file_id`, `file_name`, `mime_type`, `size_bytes`, `sha256`, `download_path`. Путь скачивания уже включает внутренний префикс API; он разрешается относительно адреса сервера. Обработчик проверяет размер и SHA-256 скачанного файла.

`limits` содержит `max_file_bytes`, `max_expanded_bytes`, `max_files`: допустимый размер одного файла, общий размер выделенных файлов и число резюме на исходник. Если `should_process=false`, обработка больше не требуется.

Для нового выделенного файла разборщик передаёт такую `metadata`:

```json
{
  "file_name": "resume-1.pdf",
  "mime_type": "application/pdf",
  "source_file_id": "30000000-0000-4000-8000-000000000001",
  "archive_path": null,
  "pages": [1, 2]
}
```

Все пять полей обязательны. `source_file_id` — входной файл команды; `archive_path` — безопасный относительный путь внутри архива либо `null`; `pages` — номера исходных страниц с 1 либо пустой список. Имя и MIME должны соответствовать переданному файлу.

`file_key` — постоянный ключ выделенного резюме, например `resume-1`, до 80 латинских букв, цифр, `_` или `-`. Повтор той же загрузки с теми же данными до сохранения результата возвращает прежний `file_id`. Изменение содержимого под занятым ключом не допускается.

## 5. Результаты обработчиков

### Разборщик

Разборщик выделяет отдельные резюме из архива или сборного PDF. Страницы одного кандидата остаются одним резюме. Каждый новый файл сначала передаётся через `PUT output`; в результате указываются полученные идентификаторы:

```json
{
  "status": "completed",
  "files": [{"file_id": "40000000-0000-4000-8000-000000000001"}],
  "errors": []
}
```

Если исходный PDF уже содержит одно резюме, можно вернуть его исходный `file_id` без копирования. Ошибки отдельных частей архива записываются в `errors` как объекты с `path`, `code`, `message`; исправные резюме при этом сохраняются. Если пригодных резюме нет, возвращается ошибка всей операции.

### Оценщик

В `requirements.targets` передаётся массив целей такого вида:

```json
{
  "id": "50000000-0000-4000-8000-000000000001",
  "name": "Разработчик",
  "education": "Высшее техническое образование",
  "experience": "Не менее трёх лет разработки на Python",
  "keywords": ["Python"],
  "stop_factors": [],
  "comment": ""
}
```

Для каждой цели оценщик возвращает ровно одну оценку с тем же идентификатором:

```json
{
  "status": "completed",
  "candidate": {
    "last_name": null,
    "first_name": null,
    "middle_name": null,
    "phone": null
  },
  "evaluations": [{
    "target_id": "50000000-0000-4000-8000-000000000001",
    "score": 80,
    "criteria": [
      {"name": "education", "status": "unknown", "explanation": "Образование не указано."},
      {"name": "experience", "status": "matched", "explanation": "Указан соответствующий опыт."},
      {"name": "keywords", "status": "matched", "explanation": "Python указан в навыках."}
    ],
    "matched_keywords": ["Python"],
    "triggered_stop_factors": [],
    "explanation": "Опыт и навыки соответствуют; образование неизвестно."
  }]
}
```

Баллы — от 0 до 100. Обязательны три критерия: образование, опыт, навыки. Значения их `status`: `matched` — соответствует, `partial` — частично, `not_matched` — не соответствует, `unknown` — нет сведений. Неизвестные ФИО и телефон возвращаются как `null`; сведения не выдумываются. Алгоритм оценки принадлежит оценщику, приложение не рассчитывает второй балл.

### Ошибка документа

Оба обработчика используют одну форму:

```json
{
  "status": "failed",
  "error": {
    "code": "TEXT_EXTRACTION_FAILED",
    "message": "Не удалось прочитать текст резюме."
  }
}
```

Коды ошибок документа: `UNSUPPORTED_FORMAT` — формат не поддерживается; `INVALID_FILE` — источник повреждён или защищён; `LIMIT_EXCEEDED` — превышены ограничения; `CANNOT_SEPARATE_RESUMES` — нельзя разделить кандидатов; `TEXT_EXTRACTION_FAILED` — нельзя прочитать текст.

Временные сбои зависимости (`PROCESSOR_UNAVAILABLE`) и вычисления (`PROCESSING_TIMEOUT`) до истечения срока приводят к повторной доставке, а не к окончательной ошибке документа. `DELIVERY_LIMIT_EXCEEDED` фиксирует API, когда брокер исчерпал доставки.

Результат передаётся непосредственно в тело `POST result`, без обёртки и без дополнительных `job_id`/`attempt`. Первый сохранённый результат не заменяется повторным. Сообщения ошибок не содержат трассировок и секретов.

## 6. Подтверждение и повтор задания

| Ситуация | Действие обработчика |
| --- | --- |
| API принял результат или постоянную ошибку: `200 {"accepted":true}` от `POST result` | Подтвердить команду: `basic.ack` |
| `should_process=false`, задача удалена/закрыта (404/410) или срок обработки истёк | Прекратить работу и подтвердить команду |
| Временный сбой сети, API или модели до истечения срока | Вернуть команду для повтора: `basic.reject(requeue=true)` |
| Неверная команда, подпись, права или несовпадение с очередью | Отклонить без повтора: `basic.reject(requeue=false)`; сообщение попадёт в очередь ошибок |

Ответ на загрузку файла или уведомление о ходе обработки ещё не подтверждает результат. Если ответ `POST result` потерян, команда возвращается для повтора. Повторную доставку и задержку обеспечивает RabbitMQ; обработчик не создаёт новую команду и не меняет `attempt`.

Любой ответ 409 не означает успех: нужно проверить `GET input`. Если задание уже неактуально — подтвердить команду; если оно активно — считать это ошибкой интеграции. Аналогично, 401 из-за истёкшего проверенного токена означает остановку, а неверная подпись или права — отклонение без повтора.

Подтверждение выполняется только на том AMQP-канале, где получена команда, и только для неё. При потере соединения неподтверждённую доставку возвращает брокер. Обработчик прекращает работу после закрытия задания и соблюдает его срок и ограничения.
