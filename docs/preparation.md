# Подготовка и включение обработки

Дата: 9 ноября 2026 года. Обработчики prepare/evaluate реализуются в другой ветке.

## Локальный запуск

1. Заполнить постоянные PostgreSQL/S3 credentials в `.env` по `.env.example`.
2. Выполнить `npm run prepare:environment`. Команда сохраняет существующие настройки,
   создаёт отсутствующие секреты, четыре отдельные RSA-пары и конфигурацию прав S3
   в `.secrets`. Секреты не выводятся и не входят в Git или Docker build context.
3. Выполнить `docker compose up -d --build`. Flyway применяет миграции V1–V7;
   s3-init создаёт постоянный bucket и `guest-temporary`, rabbitmq-init объявляет очереди обработки.
4. Открыть `http://localhost:3000`. До подключения обработчиков загрузки принимаются
   и ожидают их в RabbitMQ. Создать сотрудника командой `npm run user:create`
   с переменными `HR_USER_LOGIN`, `HR_USER_NAME`, `HR_USER_PASSWORD` (пример в README).

V6 `contact_provenance` восстановлена из существующей истории основной БД;
сегодняшние изменения авторизации и обработки объединены в одну V7:
таблицы `users`, `sessions`, `processing_tasks`, `processing_outbox`.
Миграции V1–V6 сохранены без изменений. На основном стенде история только
сегодняшних V7/V8 согласована с объединённой V7 после проверки схемы и сохранности данных.
Для повторного использования тома
брокера нужно сохранить прежний `RABBITMQ_NODE_HOSTNAME`; на новом окружении
используется стабильное значение `rabbitmq` из `.env.example`.

При обновлении установки с прежними именами `.v2` сначала остановить приём
новых заданий и завершить ранее принятые задания. Сделать резервную копию,
применить миграции и запустить `rabbitmq-init`, затем обновить API и обработчики.
Старые очереди и обменники удалять только после проверки отсутствия сообщений
и потребителей. Их имена не переименовываются автоматически средствами RabbitMQ.

Для запуска только гостевого контура: `docker compose up -d frontend auth-check guest-api clamav`.
PostgreSQL и backend для этого не требуются. При отказе брокера новые гостевые
задания не подтверждаются; сохранённые отчёты читаются из S3.

В рабочей среде задать HTTPS `APP_ORIGIN` и обеспечить TLS на входе. HttpOnly,
SameSite=Lax и Secure вычисляются API; HTTP разрешён только для localhost.
Пары ключей авторизации, guest-job, authorized-job и guest-cookie не взаимозаменяемы.
Смена ключа закрывает доступ по ранее выданным токенам, поэтому ротацию планируют
с учётом уже принятых задач. Повторный запуск подготовки не заменяет ключи.

## Подключение образов из другой ветки

Основной Compose содержит профиль `processing` с одним `resume-parser` и одним
`resume-evaluator`. Задать `PREPARE_IMAGE` и `EVALUATE_IMAGE`, затем выполнить
`docker compose --profile processing up -d`. Образы должны предоставлять собственный
HEALTHCHECK, основанный на `GET /health`, и выполнять [общий контракт](processing-services-contract.md).

| Переменная обработчика | Значение |
| --- | --- |
| `PORT` | 8001 для parser, 8002 для evaluator |
| `GUEST_AMQP_URL` | Учётная запись операции в `hr-guest` |
| `AUTHORIZED_AMQP_URL` | Та же операция в `hr-authorized` |
| `GUEST_API_BASE_URL` | `http://guest-api:3002/internal/guest` |
| `AUTHORIZED_API_BASE_URL` | `http://backend:3001/internal/app` |
| `GUEST_JOB_PUBLIC_KEY_FILE` | `/run/secrets/guest-job-public` |
| `AUTHORIZED_JOB_PUBLIC_KEY_FILE` | `/run/secrets/authorized-job-public` |

Закрытых ключей, S3/PostgreSQL credentials и сетей хранилищ у обработчиков нет.
Токен берётся из AMQP-заголовка `x-job-token`; HTTP использует Bearer. Команда не
содержит URL, файла, критериев или результата. Критерии возвращаются только evaluate.
Максимум: 50 МБ на файл, 200 выходных резюме и 250 МБ выходов на исходник.

`PUT output` использует multipart `file` + `metadata`. Повтор `file_key` с тем же
содержимым возвращает прежний ID. Для evaluate проверяется ровно одна оценка на
каждый ID из `requirements.targets`. Неизвестные ФИО/телефон — null.
Критерии: education/experience/keywords, статусы matched/partial/not_matched/unknown.
API сохраняет первый валидный результат; повтор восстанавливает публикацию его
события с тем же ID. Успешный HTTP result означает сохранение и confirm события.

## Доставка и эксплуатация

Зафиксирован RabbitMQ `4.3.6-management-alpine`, соответствующий существующему основному стеку. В ранее проверенном образе 4.3.0 ключи
`delayed-retry-*` не принимаются валидатором policy, поэтому они заданы как
`x-delayed-retry-*` при объявлении quorum queues: all, 1000–30000 мс. Это штатный
механизм брокера, проверенный по реальному времени повторной доставки. Остальные
параметры задаются policy: delivery-limit=5, consumer-timeout=1200000,
max-length-bytes=134217728, overflow=reject-publish и at-least-once DLX.
Конфигурация согласована с [документацией RabbitMQ](https://www.rabbitmq.com/docs/4.3/quorum-queues)
и проверена интеграционным тестом на указанном образе.

AMQP 0.9.1 при временной ошибке использует basic.reject(requeue=true), а не
basic.nack. DLQ исключена из рабочей policy; delivery-limit=-1. Гостевая DLQ
имеет технический TTL 24 часа. Публикации mandatory + publisher confirms;
consumer событий подтверждает сообщение после состояния и всех производных
публикаций. Чужие токены отклоняются до чтения состояния своего контура.

Для наблюдения: `docker compose logs guest-api backend rabbitmq-init`,
health guest-api с `atomic_storage`, `/api/app/processing/queue` после входа.
Ошибка очистки сообщает число задач, оставленных для следующего прохода.
В логах нет пользовательского содержимого или токенов. При необходимости UI
брокера доступен через отдельный администраторский туннель; публичного порта нет.

SeaweedFS использует bucket-scoped identities и лимит 32 тома: прежнего лимита
8 не хватало для двух bucket при стандартном росте томов. Guest API перед
включением выполняет пять раундов конкурентного conditional create/CAS, по
восемь writers. При нарушении атомарности гостевые endpoints отвечают 503.

Очистка guest-api не восстанавливает задания: она фиксирует deadline, удаляет
файлы и оставляет минимальную отметку до created_at + 24 часа. Первый download
не удаляет отчёт. Постоянные задачи и намерения публикации сохраняются в БД;
backend повторяет неподтверждённое после рестарта. Backup сохраняет постоянный
bucket и БД с outbox; восстановление не меняет resume leases. Временный bucket,
буферы Nginx и рабочие каталоги не копируются. `.secrets` сохраняют отдельно.

## Переход с v1

До переключения завершить старые задания на прежней ревизии с её worker/rank
bridge и сохранить резервную копию. Новая ветка не читает очереди v1. После
опустошения старых очередей остановить прежние обработчики и развернуть текущую схему.
Не запускать оба протокола для одного задания. Применённые миграции V1–V5 и
постоянные данные сохраняются; прежние публичные API возвращают 404 без алиасов.

## Проверки

`npm run build`, `npm test`, `npm run test:architecture`, `npm run test:processing`.
Последняя команда строит отдельный project `hr-dam-processing-qa`, использует только
синтетические документы и протокольных peers, проверяет гостя без БД/backend,
Nginx, реальные S3 CAS и RabbitMQ retries/DLQ, авторизацию, сохранение кандидатов,
рестарты outbox и браузерные вход/выход. Артефакты браузера — `.qa/processing`.
Тестовый ClamAV stub находится только в QA override. Для браузера по умолчанию
используется установленный Chrome; можно задать `TEST_BROWSER_CHANNEL`.

После объединения веток повторить эти сценарии с реальными образами и проверить
алгоритмы разделения ZIP/PDF, качество оценки, лимиты ресурсов и очистку их
рабочих каталогов. Эти проверки относятся к поставке двух обработчиков.
